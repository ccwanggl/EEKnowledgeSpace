# 中断体系开发

"事件来了通知我"是驱动与轮询的分界线。[[006-GPIO和Pinctrl子系统|GPIO 按键中断]]是最直观的中断应用，但中断体系本身是一套独立机制：硬件中断号如何映射、硬中断上下文能做什么、耗时处理往哪里放、多核时代中断落在哪个 CPU。本篇建立完整体系，代码沿用上篇的按键例子但把理论讲透。

## 硬件基础：从中断源到 Linux IRQ 号

- **GIC（Generic Interrupt Controller）**：ARM 标准中断控制器，RK3588 用 GICv3。中断类型分三类：**SPI**（共享外设中断，芯片外设几乎全走它）、**PPI**（私有，如 per-CPU 定时器）、**SGI**（核间软中断）。
- **irq domain**：datasheet 里的硬件中断号（hwirq，如 GIC 的 SPI 号）不等于内核的 Linux IRQ 号。irq domain 完成映射：`dtsi 的 interrupts = <GIC_SPI N …>` → GIC 驱动解析 → 分配虚拟 IRQ。驱动**永远通过 API 取 IRQ 号**（`platform_get_irq`、`gpiod_to_irq`），不要硬编码数字。
- **级联（chained）**：GPIO 中断不是 GIC 直连——RK 的 pinctrl 驱动内含 gpio irqchip，GIC SPI 先到达 pinctrl 驱动，它再分发到具体 GPIO。多级级联对用户透明，但解释了为什么"GPIO 都支持中断、而具体触发类型由 dts/gpio 层定义"。

对照 MCU：NVIC 里"中断号=向量表槽位"的简单关系，到 Linux 变成 domain 映射 + 级联的两级结构，见 [[04-Microcontrollers/06-中断与DMA深入/001-中断系统|中断系统（MCU 视角）]]。

## API 谱系：三代演进

| 代际 | 接口 | 现状 |
|------|------|------|
| 1.0 | `request_irq(irq, handler, flags, name, dev_id)` | 全程硬中断上下文，处理函数不能睡眠 |
| 2.0 | `request_threaded_irq(irq, primary, thread_fn, flags, name, dev_id)` | 拆成上下两半：primary 在硬中断（只确认/快速处理），thread_fn 在内核线程（可睡眠） |
| 3.0 | `devm_request_threaded_irq(dev, …)` | 2.0 + devm 生命周期托管，现代驱动的默认选择 |

关键标志：

- `IRQF_TRIGGER_RISING/FALLING/HIGH/LOW`：触发方式，与 dts `interrupts` 里的类型一致（GPIO 场景由 `gpiod_to_irq` + 标志表达）。
- `IRQF_ONESHOT`：threaded IRQ 必配——primary 为 NULL 时内核自动加；含义是线程处理完前屏蔽该中断线，防抖动重入。
- `IRQF_SHARED`：多个设备共用一条中断线，primary 必须返回 `IRQ_NONE`/`IRQ_HANDLED` 诚实报告"是不是我的"。

## 上半部与下半部：能睡不能睡

硬中断上下文有硬性约束：**不能睡眠**（调度器状态不允许，睡眠即 "sleeping function called from invalid context" oops）、不能持锁睡眠、要尽量快（同中断线的其他设备在等）。实际工作分配：

- **几微秒的事**（读状态寄存器、清中断标志、ACK）放硬中断；
- **可能睡眠的事**（消抖等待、I2C/SPI 读写、分配内存、上报 input 事件）放下半部。

下半部的现代选项：

| 机制 | 上下文 | 说明 |
|------|--------|------|
| **threaded IRQ** | 专用内核线程 | 首选：与中断线绑定、自动屏蔽管理、可加 RT 优先级 |
| workqueue | 共享工作队列 | 自己管理 work 结构，适合不绑定中断线的异步任务 |
| tasklet | 软中断 | 不能睡眠且同实例串行，内核已不推荐新代码使用 |

## 中断与设备树

片上外设走 GIC 直挂（见 [[004-设备树开发]] 的 interrupts 绑定）：

```dts
interrupt-parent = <&gic>;
interrupts = <GIC_SPI 33 IRQ_TYPE_LEVEL_HIGH>;
interrupt-names = "ready";
```

```c
int irq = platform_get_irq_byname(pdev, "ready");
/* 或 platform_get_irq(pdev, 0); */
devm_request_threaded_irq(dev, irq, NULL, my_thread_fn,
                          IRQF_ONESHOT, "mydev", priv);
```

GPIO 中断走级联路径：`gpiod_to_irq(btn)` 拿 IRQ，触发标志在申请时给：

```c
int irq = gpiod_to_irq(priv->btn);
devm_request_threaded_irq(dev, irq, NULL, btn_thread_fn,
                          IRQF_TRIGGER_FALLING | IRQF_ONESHOT, "mybtn", priv);
```

完整按键驱动代码见 [[006-GPIO和Pinctrl子系统]]（两者合读：006 讲管脚，本篇讲中断）。

## 亲和性：中断落在哪个 CPU

多核 SoC 上中断默认由内核调度到任意 CPU，`irqbalance` 会自动迁移。对延迟敏感的驱动（运动控制、数据采集）应绑核：

```bash
cat /proc/interrupts                          # 每个中断在各 CPU 的计数
echo 2 > /proc/irq/123/smp_affinity           # 掩码：CPU1（bit0=CPU0）
chrt -f 50 pgrep -f "irq/123-mybtn"           # 提升中断线程 RT 优先级
```

`/proc/irq/N/` 目录下还有 `affinity_hint`（驱动建议）与 `node`（NUMA）。实测原则：绑核前先跑 ftrace 看 handler 实际耗时，优化代码优先于调度杂技。

## 调试

- **`/proc/interrupts`**：注册了没（行存在）、触发了没（计数增长）、分布均匀吗（各 CPU 列）。第一诊断工具。
- **ftrace 事件**：`/sys/kernel/tracing/events/irq/irq_handler_entry|exit`、`gpio/gpio_value` 等，配合 `function_graph` 看 handler 耗时（见 [[008-驱动调试排错]]）。
- **missing interrupt**：计数不动——查触发沿/电平语义、上拉、复用；计数狂涨——查消抖、电平触发未清标志、共享中断返回值错误。

## 常见陷阱

- **触发沿与有效电平不对应**：低有效按键（上拉，按下为低）应配 `IRQF_TRIGGER_FALLING`；配反的症状是按一次记两次或毫无反应。
- **硬中断里睡眠**：oops "sleeping function called from invalid context"，栈回溯指向 `msleep/mutex_lock`——把该段挪进线程函数。
- **消抖缺失**：机械按键 5~20ms 抖动，软件底线是线程里 `msleep(10)` 后复核电平，硬件 RC/施密特更可靠。
- **共享中断返回错**：`IRQF_SHARED` 下 primary 认不出自己的中断时返回 `IRQ_NONE`，内核才好转交下一个共享者；返回 `IRQ_HANDLED` 会吞掉别人的中断。
- **中断里操作被并发访问的状态**：线程与进程上下文并发，计数/队列需要锁或原子操作保护。

## 检查清单

- IRQ 一律 API 获取，触发标志与硬件电平语义一致。
- 硬中断只做不可少的事；可能睡眠的路径全在线程。
- 共享中断 primary 诚实返回；消抖落实。
- `/proc/interrupts` 验证注册与计数，ftrace 验证耗时。

## 实验

1. 运行 [[006-GPIO和Pinctrl子系统|按键驱动]]，`cat /proc/interrupts | grep mybtn` 确认行存在，按键观察计数按 CPU 列增长。
2. 把触发沿改错（`IRQF_TRIGGER_RISING`），观察计数异常（抖动多计），再改回。
3. `smp_affinity` 把中断绑到 CPU1，连续按键对比绑核前后的调度抖动（ftrace 看 handler 间隔）。
4. ftrace 使能 `irq:irq_handler_entry/exit`，抓一次按键的完整时序：硬中断 → 线程调度 → 线程执行。
