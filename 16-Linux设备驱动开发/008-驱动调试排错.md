# 驱动调试排错

驱动跑在内核态，没有 printf 重定向、没有 gdb 单步的舒适区，调试依赖一套内核自带工具链。本篇给出驱动开发的最小调试工具箱：日志分级与 dynamic debug、ftrace 调用链、debugfs 状态查看、oops 初步分析。内核编译与部署工作流见 [[009-工程实战能力]]。

## 调试工具箱

| 工具 | 用途 | 入口 |
|------|------|------|
| `dmesg` | 一切异常的**第一现场**：probe 失败、oops、vermagic | 全文已见，`-w` 跟踪 |
| dynamic debug | 按需打开 `pr_debug/dev_dbg` 日志，不改代码不重编 | `/sys/kernel/debug/dynamic_debug/control` |
| debugfs | 查看子系统内部状态（pinctrl、GPIO、regmap） | `/sys/kernel/debug/` |
| ftrace | 看函数调用链与时序（probe 为什么不执行？） | `/sys/kernel/tracing/` |
| `/proc/interrupts` | 中断计数：注册了没？触发了没？ | 直接 cat |

## dynamic debug：日志开关在运行时

内核及驱动里的 `pr_debug()` 默认不输出。内核开启 `CONFIG_DYNAMIC_DEBUG` 后（发行版内核通常已开，`zcat /proc/config.gz | grep DYNAMIC_DEBUG` 确认），运行时精确控制：

```bash
# 打开某文件的全部 debug 日志
echo "file drivers/gpio/gpio-rockchip.c +p" | sudo tee /sys/kernel/debug/dynamic_debug/control
# 按函数名
echo "func sht30_probe +p" | sudo tee /sys/kernel/debug/dynamic_debug/control
# 查看当前所有开关
sudo cat /sys/kernel/debug/dynamic_debug/control
# 撤销
echo "file drivers/gpio/gpio-rockchip.c -p" | sudo tee /sys/kernel/debug/dynamic_debug/control
```

也可以启动参数级联：`dyndbg="file drivers/i2c/* +p"` 写进 bootargs，开机即生效——在没有串口控制台之前就要日志时用它。

为什么推荐 `pr_debug` + dynamic debug 而不是 `pr_info`：发行版内核日志级别下 debug 日志零开销零噪音，出问题时一条 echo 打开，定位完关掉。**写驱动时的日志习惯直接决定未来的调试成本**。

## ftrace：看 probe 为什么没执行

compatible 写对了、模块加载了，probe 却不被调用——这类"匹配链路"问题靠日志猜不如看调用链。function_graph 跟踪器：

```bash
cd /sys/kernel/tracing
echo function_graph > current_tracer
echo 'platform_match of_platform_match sht30_probe platform_probe' > set_ftrace_filter
echo 1 > tracing_on
# 触发：加载模块 / 重新 probe
cat trace
```

输出形如：

```
 1)               |  platform_match() {
 1)               |    of_driver_match_device() {
 1)   1.234 us    |      of_match_device();
 1)   2.876 us    |    }
 1) + 12.345 us   |  }
 1)               |  platform_probe() {
 1)               |    sht30_probe() {
```

match 返回了 0（没走到 probe）还是 probe 内部出错，一目了然。tracepoint 事件（`/sys/kernel/tracing/events/`）还能看 i2c/spi 事务：`events/i2c/enable`。图形前端有 `trace-cmd` + KernelShark。

## oops 的初步读法

```
Unable to handle kernel NULL pointer dereference at virtual address 0000000000000010
...
Call trace:
  gpiod_set_value+0x24/0x40
  btnled_probe+0x88/0x1a0 [btnled]
```

- 前两行给异常类型与地址（NULL+0x10 提示解引用了一个结构体成员而结构体指针为 NULL——多半是 `devm_xxx_get` 的返回值没检查）。
- Call trace 从下往上是自己的调用路径，从上往下是出错现场。
- 拿编译出的带符号 `vmlinux` 或模块 .ko 反查行号：

```bash
aarch64-linux-gnu-addr2line -e drivers/gpio/gpio-rockchip.o -f -C 0x24
# 有 KASLR 时用内核自带脚本：
./scripts/decode_stacktrace.sh vmlinux < kernel_log.txt
```

oops 之后内核不一定死（非中断上下文可杀进程），但驱动状态已经可疑，先查空指针解引用这条最高频根因。

## 常见陷阱

- **dynamic debug 开关不生效**：内核没开 `CONFIG_DYNAMIC_DEBUG`，或控制文件路径在部分内核是 `/proc/sys/debug/`（老内核）。先 grep 配置。
- **ftrace 无输出**：`set_ftrace_filter` 函数名不对（看 `available_filter_functions`）；或被 `tracing_on` 关掉。

## 检查清单

- `pr_debug` 写关键路径（probe 返回值、状态机跳转、错误分支），dynamic debug 可开。
- oops 现场完整保存（串口日志比截图可靠），先用 addr2line 定位再改代码。

## 实验

1. `echo "file drivers/gpio/gpio-rockchip.c +p" > control`，操作 [[006-GPIO和Pinctrl子系统|按键]] 观察 debug 日志，再 `-p` 关闭。
2. function_graph 跟踪 `sht30_probe`：故意把 dts 的 compatible 改错，观察 match 返回与 probe 缺失的完整过程。
