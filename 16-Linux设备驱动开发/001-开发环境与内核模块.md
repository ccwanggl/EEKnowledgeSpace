# 开发环境与内核模块

驱动开发的第一步不是写驱动，而是打通"写代码 → 编译 → 加载 → 看日志"的最小闭环。本文先准备 RK3588 开发环境，再建立这个闭环，后续所有驱动实验都复用它。

## 开发环境准备

| 组件 | 说明 |
|------|------|
| **串口控制台** | RK 调试 UART（波特率 `1500000`），`picocom -b 1500000 /dev/ttyUSBx`。改内核/调启动问题时的**最后退路**，比 SSH 优先 |
| **交叉工具链** | `sudo apt install gcc-aarch64-linux-gnu`，版本尽量与发行版内核编译器一致（见 [[009-工程实战能力]] 版本对齐） |
| **网络通道** | SSH + `scp` 传 .ko/.dtb；开发板与主机同网段，固定 IP 或 mDNS |
| **板上包管理** | Armbian/Ubuntu Rockchip 用 `apt` 装 `i2c-tools`、`gpiod`、`linux-headers` 等 |

## 为什么驱动是模块

- **模块（.ko）是可动态加载的内核代码**。驱动开发期必须模块化——每改一行都重刷整个内核是不可接受的；模块出错可以卸载修正后秒级重载。
- 模块不是独立程序：没有 `main()`，入口由 `module_init()`/`module_exit()` 注册；只能调用内核导出（`EXPORT_SYMBOL`）的符号。
- `MODULE_LICENSE("GPL")` 不只是声明：非 GPL 许可证的模块将无法访问内核标记为 `EXPORT_SYMBOL_GPL` 的符号，实际开发中几乎必须使用 GPL。

## 最小模块

```c
#include <linux/module.h>
#include <linux/init.h>

static int __init hello_init(void)
{
    pr_info("hello: init\n");          /* 等价于 printk(KERN_INFO ...) */
    return 0;                          /* 返回非 0 表示加载失败 */
}

static void __exit hello_exit(void)
{
    pr_info("hello: exit\n");
}

module_init(hello_init);
module_exit(hello_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("minimal module example");
MODULE_AUTHOR("me");
```

配套 Makefile（内核 Kbuild 体系，写法固定）：

```makefile
KDIR ?= /lib/modules/$(shell uname -r)/build

obj-m += hello.o

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean
```

`$(MAKE) -C $(KDIR) M=$(PWD)` 的含义：进入内核源码/头文件目录，用它的 Kbuild 规则编译当前目录下的模块。驱动不能脱离内核树单独编译——它引用的头文件、符号表、结构布局都由目标内核决定。

## 两条编译路径

**板上原生编译**（简单，板子性能弱、适合小模块）：

```bash
sudo apt install linux-headers-$(uname -r)   # Armbian/Ubuntu 源里通常有
make
```

前提是 `/lib/modules/$(uname -r)/build` 符号链接存在且指向正确源码。

**交叉编译**（推荐，快且可脚本化）：

```bash
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
     -C ~/src/linux-orangepi M=$PWD modules
```

这里 `KDIR` 必须是一棵**已配置的内核源码树**（有 `.config`，且至少跑过 `make ARCH=arm64 defconfig && make modules_prepare`，最好完整编译过一次）。网上下载的裸源码不能直接编模块。

## vermagic 与版本匹配

`modinfo hello.ko` 可以看到：

```
vermagic:       6.1.43-rockchip64 SMP preempt mod_unload aarch64
depends:
```

`vermagic` 是编译时目标内核的"指纹"（版本号、SMP/preempt 配置、mod_unload 等）。加载时与运行内核逐一比对，不一致即拒绝：

```
insmod: ERROR: could not insert module hello.ko: Invalid module format
dmesg 尾部: version magic '5.10.160 ...' should be '6.1.43 ...'
```

**结论：.ko 与运行内核严格配对。** 开发板升级内核后所有 .ko 都要重编；这也是交付驱动时必须连同内核版本一起说明的原因。`depends` 列出依赖的其它模块——`insmod` 不解析依赖，`modprobe` 解析（模块需先 `make modules_install` 到 `/lib/modules/$(uname -r)` 并 `depmod -a` 建立依赖索引）。

## 加载、查看与卸载

```bash
sudo insmod hello.ko        # 加载；失败先看 dmesg，不要猜
sudo rmmod hello            # 卸载
lsmod | grep hello          # 已加载列表
modinfo hello.ko            # 查看模块元信息
dmesg -w                    # 跟踪内核日志（-w 持续输出）
```

`printk` 有 8 个级别（`KERN_EMERG` … `KERN_DEBUG`），是否上屏由 console loglevel 决定：

```bash
cat /proc/sys/kernel/printk        # 4 个值：当前控制台级别 默认级别 ...
echo 8 > /proc/sys/kernel/printk   # 控制台级别调到 7（DEBUG 也上屏）
```

驱动代码里的惯例：正式路径用 `dev_info/dev_err`（带设备名、自动带级别），调试用 `pr_debug`（默认不上屏，配合 [[008-驱动调试排错|dynamic debug]] 按需开启），避免用裸 `printk` 刷屏。

开机自动加载：把模块名写进 `/etc/modules-load.d/xxx.conf`（一行一个模块名），配合模块文件已安装到 `/lib/modules/$(uname -r)`。

## 常见陷阱

- **dmesg 没有预期输出**：先查 printk 级别，再查是不是加载了同名旧模块（`modinfo $(find /lib/modules -name 'hello.ko') | grep filename` 看实际加载的是哪个文件）。
- **`Invalid module format`**：99% 是 KDIR 与运行内核不匹配（apt 升级内核后 headers 未同步、或用了别的源码树）。
- **源码树未配置**：报"找不到 include/generated/xxx"之类错误，回源码树先 `make defconfig && make modules_prepare`。
- **把模块当应用调试**：模块没有 stderr/退出码语义，`insmod` 的报错经常只是"加载失败"，真实原因永远在 `dmesg` 里。

## 实验

1. 板上执行 `uname -r`，确认 `/lib/modules/$(uname -r)/build` 存在；不存在则安装对应 headers。
2. 交叉编译 `hello.ko`：`scp` 到开发板 → `sudo insmod hello.ko` → `dmesg | tail` → `modinfo` → `sudo rmmod hello`。
3. 故意用一个版本不符的源码树编译，复现并读懂 vermagic 报错原文。
