# 工程实战能力

实验代码能跑与产品驱动能交付之间，隔着一套工程能力：内核改得动、补丁管得住、版本对得齐、质量控得住、出了问题退得回。本篇以 RK 平台为背景，把前面各篇的实验能力升级为可重复、可交付的工作流。

## 识别你的内核

RK 平台的内核来自三个层级之一：**内核主线**（RK3588 支持逐步完善中）、**rockchip-linux 官方 fork**（github.com/rockchip-linux/kernel）、**发行版 fork**（Armbian、OrangePi 各自维护）——开发板镜像几乎都是第三方 fork。动手前先确认出处：

```bash
uname -r                    # 发行版内核名（如 6.1.43-rockchip64）
cat /etc/os-release         # 发行版
ls /boot                    # Image/vmlinuz、dtb 目录、config 文件
```

内核名带 `rockchip64`/`rk35xx` 字样基本可判断为 Armbian 系。源码树必须取**与运行内核同源同分支**的 fork，混用不同 fork 的 dts/驱动是自找麻烦。

## 获取源码与配置

```bash
git clone <与镜像对应的内核 fork> && cd linux
git checkout <镜像所用的分支/tag>
zcat /proc/config.gz > .config    # 需 CONFIG_IKCONFIG_PROC，发行版内核通常开启
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- olddefconfig
```

`zcat /proc/config.gz` 优先于 `/boot/config-*`：它保证配置就是**正在运行**的这个内核的。

## 编译与部署三件套

```bash
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc) Image modules dtbs
make ARCH=arm64 INSTALL_MOD_PATH=$PWD/_rootfs modules_install   # 模块暂存
# 产物：arch/arm64/boot/Image、arch/arm64/boot/dts/rockchip/rk3588s-*.dtb、_rootfs/lib/modules/
```

部署到开发板的是三件套：内核镜像（`/boot` 下 `Image`/`vmlinuz`）、dtb（`/boot/dtb/rockchip/`）、模块目录（`/lib/modules/<新版本>/`，板上 `sudo depmod -a`）。三者必须同源同次编译。

**最干净的交付方式是 deb 包**：

```bash
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- bindeb-pkg -j$(nproc)
# 产出 linux-image-*.deb / linux-headers-*.deb
# scp 到板上 dpkg -i：内核、dtb、模块、initramfs 钩子一次到位
# headers 包装好后，[[001-开发环境与内核模块|外置模块编译]] 才有准确的 KDIR
```

## 补丁管理

自有修改（驱动、dts、配置）以 git 提交叠在 fork 分支上：

```bash
git commit -m "drv: add mycore driver"          # 驱动、dts 分开提交
git format-patch -o patches/ origin/HEAD..      # 导出交付
git am patches/*.patch                          # 应用/迁移
```

vendor 内核升级时 `git rebase` 自己的提交栈，冲突就地解决——这比维护一堆零散 `.patch` 文件可靠得多。提交信息遵循内核惯例（`drv:`、`arm64: dts:` 等前缀），为将来向上游提交留好格式底子。风格门禁：`scripts/checkpatch.pl --strict` 先过一遍。

## 版本对齐：四处一致

| 项 | 对齐目标 |
|----|---------|
| 内核 Image 与 dtb | 同一次编译 |
| 模块 .ko | 对同一源码树编译（[[001-开发环境与内核模块|vermagic]] 强校验） |
| 交叉编译器 | 与编译该内核的 gcc 大版本一致 |
| dts 与驱动 | compatible、绑定、of API 语义随版本演进，配套更新 |

升级内核后四件事：重编模块、重编/替换 dtb、板上 `depmod -a`、验证 `modinfo vermagic`。

## 质量门禁与自检

合入前过三道工具闸 + 一张人工清单：

```bash
scripts/checkpatch.pl --strict patches/*.patch   # 风格
make C=2 drivers/mydriver/                       # sparse：类型/地址空间检查
# coccinelle 语义补丁查空指针解引用、资源泄漏等模式（scripts/coccinelle/）
```

人工清单（比工具更常抓虫）：

- 资源申请/释放逐路径配对（devm 之外的手动资源）；
- 错误路径不留半截状态：probe 中途失败，`dev_err_probe` 打日志并返回；
- 并发面清单：哪些状态被进程/中断/多实例共享，各用什么保护；
- 日志规范：`pr_debug` 留调试钩子、`dev_err` 带上下文，正式路径不刷屏；
- 用户态输入全部校验（sysfs store、ioctl arg）。

## 交付与回退

每次改内核前必做的三件事：

1. **备份**要覆盖的文件：旧 Image/dtb、旧 `/lib/modules/<版本>` 整个目录；
2. **串口控制台**可用（[[001-开发环境与内核模块|环境准备]]）——图形/网络挂了时的唯一入口；
3. 新内核先以独立名字（`Image.test`）放入引导配置，验证通过再替换正式项；extlinux.conf 保留旧内核条目可回选。

交付物打包：deb 包 + 补丁栈（format-patch）+ 一页 CHANGELOG（改了什么、依赖哪个内核版本、如何回退）。

## 常见陷阱

- **编出的 dtb 没生效**：发行版启动用的是 `/boot/dtb/rockchip/`（可能带版本子目录）里的文件，替换后核对启动日志实际加载的 dtb 名（`dmesg | grep -i dtb`），或用 `dtc -I fs` 反编译运行视图（见 [[004-设备树开发]]）。
- **换了内核忘记重编模块**：vermagic 不匹配，全部 .ko 重编。
- **交叉编译器不一致**：内核 gcc 12 编、模块 gcc 13 编，可能加载失败或运行异常。
- **fork 混用**：从 Armbian 内核源码编出的 Image 配 OrangePi 的 dtb——寄存器定义、时钟名差异会让板子起不来。

## 检查清单

- 源码 fork/分支与运行内核同源，`.config` 取自 `/proc/config.gz`。
- 三件套同次编译、deb 交付、回退路径演练过。
- checkpatch/sparse 过闸，人工清单逐项确认。

## 实验

完整走一个驱动交付循环：板级 dts 加 `myvendor,mycore` 节点 → 驱动进源码树编译 → `bindeb-pkg` 出包 → 板上安装验证 sysfs 交互 → 故意用旧模块复现 vermagic 失败 → 恢复备份演示回退。
