# 设备树开发

设备树是驱动模型的硬件描述侧：同一内核镜像配上不同 dtb 支持不同板子，驱动的 platform 匹配、资源获取全部以它为数据源。入门概念见 [[10-RTOS与系统/05-嵌入式Linux入门/004-设备树DeviceTree|设备树（入门）]]，本篇面向驱动开发者：写得出合规节点、查得到绑定规范、调得动生效链路。

## 语法精要（驱动视角）

```dts
/ {
    chosen {                            /* 引导参数、stdout 等 */
        bootargs = "...";
    };

    mycore {                            /* 节点名 @ 前的地址要与 reg 首地址一致 */
        compatible = "myvendor,mycore"; /* 匹配的唯一凭据 */
        status = "okay";                /* "disabled"/"reserved" 时不实例化 */
        reg = <0xFDE20000 0x1000>;      /* 寄存器基址 + 长度（由 #address-cells/#size-cells 决定位数） */
        timeout-ms = <200>;             /* 自定义属性：u32 数组 */
        label = "core0";                /* 字符串 */
        reset-gpios = <&gpio4 RK_PB0 GPIO_ACTIVE_LOW>;  /* phandle 引用 + 参数 */
        power-supply = <&vcc3v3_sys>;
        interrupt-parent = <&gic>;
        interrupts = <GIC_SPI 33 IRQ_TYPE_LEVEL_HIGH>;
    };
};
```

- **phandle**：`&label` 引用其它节点；上游 dtsi 定义的 label（`&gpio4`、`&i2c1`、`&pinctrl`…）是板级 dts 的主要拼装对象。
- **`#address-cells` / `#size-cells`**：父节点声明 `reg` 用几个 u32 表示地址/长度，写子节点 `reg` 前先看父节点声明。
- **布尔属性**：`spi-cpol;` 这类无值属性存在即真。
- **unit-address**：`节点名@地址` 里的地址必须等于 `reg` 首地址，否则 dtc 报错或告警。

## 三类关键绑定

绑定（binding）= "某类节点的属性写法规范"，权威来源是内核源码 `Documentation/devicetree/bindings/`。**改 dts 前先查绑定**，比抄旧板子可靠。

### GPIO

```
led-gpios = <&gpio4 RK_PB1 GPIO_ACTIVE_LOW>;
```

`&gpio4` 指向 gpio 控制器节点（控制器声明 `#gpio-cells = <2>`，所以每引用一次带 2 个参数：引脚号 + 标志）。驱动侧 `devm_gpiod_get(dev, "led", …)` 的 con_id 取属性名去掉 `-gpios` 后缀。

### 中断

```
interrupt-parent = <&gic>;
interrupts = <GIC_SPI 33 IRQ_TYPE_LEVEL_HIGH>;
```

RK3588 走 ARM GIC：`GIC_SPI`（共享外设中断，芯片外设都用它）+ SPI 号 + 触发类型。`interrupt-names = "ready"` 配 `platform_get_irq_byname(pdev, "ready")` 使用。GPIO 中断不走 GIC 直挂，而是经 pinctrl 的 irqchip 级联（`gpiod_to_irq`，见 [[006-GPIO和Pinctrl子系统]]）。

### 时钟与电源

```
clocks = <&cru CLK_MYCORE>;
clock-names = "core";          /* 与 devm_clk_get(dev, "core") 对应 */
power-supply = <&vcc3v3_sys>;  /* regulator：<name>-supply 与 devm_regulator_get(dev, "power") 对应 */
```

时钟名定义在 `include/dt-bindings/clock/rk3588-cru.h`（各 RK 芯片有对应头文件），写 dts 前翻头文件确认名字存在。

## 内核如何消费设备树

- **启动早期** unflatten dtb 为内部树，`/sys/firmware/devicetree/base` 是它的只读镜像（调试入口）。
- **of API**（旧接口）与 **property API**（新统一接口）并存，驱动里推荐后者：

| 操作 | of API | property API（推荐） |
|------|--------|---------------------|
| 读 u32 | `of_property_read_u32(node, …)` | `device_property_read_u32(dev, …)` |
| 读字符串 | `of_property_read_string` | `device_property_read_string` |
| 读 GPIO | `of_get_named_gpio(node, "led", 0)` | `devm_gpiod_get(dev, "led", …)` |
| 取中断 | `of_irq_parse` / `irq_of_parse_and_map` | `platform_get_irq` / `fwnode_irq_get` |
| 找节点 | `of_find_node_by_path("/mycore")` | `device_get_named_child_node` |

- **实例化时机**：`of_platform_populate()` 把有 compatible 的节点转成 platform_device，此后才轮到 [[003-Linux设备模型|匹配与 probe]]。所以 dts 改了没生效时，分清是"dtb 没换"还是"节点没实例化"。

## overlay：不改主 dtb 的实验手段

把增量写成 `.dtso`，编译为 `.dtbo`：

```dts
// myoverlay.dtso
/dts-v1/;
/plugin/;

&i2c1 {
    status = "okay";
    sht30@44 {
        compatible = "myvendor,sht30";
        reg = <0x44>;
    };
};
```

```bash
dtc -@ -I dts -O dtb -o myoverlay.dtbo myoverlay.dtso
```

部署方式随发行版：Armbian 把 `myoverlay.dtbo` 放进 `/boot/dtb/rockchip/overlay/` 并在 `/boot/armbianEnv.txt` 写 `overlays=myoverlay`；OrangePi 类似（`orangepiEnv.txt`）；底层是 U-Boot 的 `fdt apply`。

- **适合**：驱动开发期的外设验证、引脚复用的快速切换。
- **不适合**：量产——overlay 叠加顺序与冲突排查成本高，产品应把最终配置回归进板级 dts 整编 dtb。

## 调试手段

```bash
# 查看运行中的设备树（与启动时dtb一致）
ls /sys/firmware/devicetree/base
cat /sys/firmware/devicetree/base/mycore/compatible | tr '\0' ' '

# 反编译启动用的 dtb（从 /proc/device-tree 或 /boot 下dtb文件）
dtc -I fs -O dts /sys/firmware/devicetree/base    # 直接反编译运行视图
dtc -I dtb -O dts rk3588s-orangepi-5.dtb > 反查.dts

# 看实例化与匹配过程
dmesg | grep -i -E "of|dtb|mycore"
ls /sys/bus/platform/devices/          # 节点是否成了设备
ls /sys/bus/platform/drivers/mycore/   # 驱动绑定了哪些设备
```

`dtc -I fs` 反编译运行视图能看到**实际生效**的属性值（包括 bootloader 改过和 overlay 叠加后的结果），是"dtb 到底换没换"的终极裁判。

## 常见陷阱

- **reg 与 unit-address 不一致**：`mycore@FDE20000` 配 `reg = <0xFDE20000 …>`，大小写无所谓但数值必须相等。
- **引用不存在的 label**：编译直接报错；跨文件引用要确认 include 顺序（`#include "rk3588.dtsi"` 在前）。
- **status 继承**：上游 dtsi 写了 `disabled`，自己节点忘了 `okay`，silently 不工作。
- **I2C 地址 7/8 位混淆**：`reg` 用 7 位地址；datasheet 给 8 位读写地址时右移一位（见 [[007-主流外设驱动]]）。
- **overlay 叠加顺序**：多个 overlay 修改同一节点时后加载的覆盖先加载的，排查冲突先看 armbianEnv.txt 里的顺序。

## 检查清单

- 节点有 compatible、status，unit-address 与 reg 一致。
- GPIO/中断/时钟/电源属性与 bindings 文档逐项核对。
- 改动后 `dtc -I fs` 反编译确认生效，再看平台设备是否实例化。

## 实验

1. `dtc -I fs` 反编译板上设备树，找到自己开发板的串口节点，读出它的 `compatible`、`reg`、`interrupts`。
2. 给 [[007-主流外设驱动|sht30]] 写 overlay 并启用，`/sys/firmware/devicetree/base/i2c@…/sht30@44` 确认节点出现、驱动绑定。
3. 故意把 `reg` 与 unit-address 改不一致，观察 dtc 告警。
