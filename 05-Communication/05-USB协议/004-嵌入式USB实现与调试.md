# 嵌入式 USB 实现与调试

到了固件这一层，USB 的难点从"协议怎么定义"变成"控制器怎么用"：端点缓冲区怎么摆、描述符表放在哪、枚举过程中的中断怎么处理、以及出问题时怎么在不改硬件的前提下判断是设备侧还是主机侧。本篇给出选型维度、固件结构要点、抓包判读方法和常见故障的定位顺序。

## 1. MCU 内置 USB 的差异

选 MCU 时先看四件事：设备/主机角色、速度等级、物理层是内置还是外接、端点缓冲的组织方式。

| 平台 | 角色与速度 | 物理层 | 备注 |
|---|---|---|---|
| STM32 系列 | USB FS Device（部分型号含 OTG_FS/OTG_HS，可做 Device/Host/OTG） | FS 内置收发器；HS 通常需 ULPI 外接 PHY | 不同子系列的 USB 外设差异较大，需逐型号核对参考手册与数据手册 |
| ESP32-S2 / S3 | USB OTG，Device 与 Host | 内置 | 与 ESP-IDF 的 TinyUSB 集成，常用于 CDC/HID/MSC/DFU |
| RP2040 / RP2350 | USB 1.1，Device 与 Host | 内置 | 控制器简单，配合 PIO 可做非标准时序外设 |
| CH32V307 | USB 2.0 FS，Device/Host/OTG | 内置 | 国产 RISC-V 方案，常见于 CDC/自定义 HID |
| nRF52840 | USB 2.0 FS Device | 内置 | 与 BLE 常同时使用，注意供电与共存 |

Full Speed 控制器通常只有少量固定端点，端点缓冲区按 2 字节或 4 字节粒度分配给各端点，总数受控制器 RAM 限制；High Speed 控制器端点更多、每端点可配更大的包，但会引入双缓冲或三缓冲来吸收主机调度抖动。ULPI 外接 PHY 的方案把模拟部分移出芯片，好处是 HS 与更好的信号完整性，代价是引脚、布局和 PHY 配置（时钟、参考电阻、寄存器初始化序列）都要按 PHY 数据手册处理——具体寄存器名与默认值必须查该 PHY 的数据手册，不能照搬其他型号。

## 2. 协议栈对比与选择依据

TinyUSB 是跨平台开源栈，覆盖 50 余款 MCU，设备侧与主机侧都有实现，类驱动（CDC、HID、MSC、MIDI、DFU、WebUSB 等）较齐全，适合多平台复用同一套设备代码。它的代价是需要自己完成移植层（时钟、中断、端点读写）与配置裁剪，资源紧张的 MCU 上要留意 RAM 占用。

STM32 USB Device Library 与 CubeMX 深度集成，生成代码快、与 ST 的中间件（如 USB Host、MSC 配合 FatFS）衔接好，适合以 STM32 为唯一平台的项目；缺点是 API 与 ST 的版本绑定较强，跨平台迁移成本高。

ESP-IDF 提供基于 TinyUSB 的设备侧组件，以及独立的 USB Host Library（主机侧 HID/MSC/CDC 支持），适合 ESP32-S2/S3 上的双角色或主机应用。MicroPython USB 适合脚本化开发与教育场景，内置 CDC/MSC 等设备类，但吞吐与实时性受解释器限制。Zephyr 的 USB 子系统与设备树、Kconfig 集成，适合已经在用 Zephyr 的项目，类驱动质量随版本演进较快。

选择时可问三个问题：目标 MCU 是否在栈的官方支持列表里（而不是靠社区移植）；需要的设备类是否有现成实现、是否要同时做主机；出问题时能否读到版本对应源码与 issue。对量产项目还要考虑许可证与长期维护，具体条款以各项目仓库的 LICENSE 为准。

## 3. 固件结构要点

端点缓冲与 FIFO 是第一个关键点。全速控制器通常按端点分配固定缓冲区，缓冲区大小会四舍五入到控制器支持的粒度，声明一个大端点可能悄悄吃掉其他端点的空间，导致端点配置失败（表现为控制器初始化返回错误或枚举到某步停止）。配置时要把所有端点的需求相加，并与控制器可用的 USB RAM 对比。

描述符表应集中定义并保持字节对齐，配置描述符集合必须连续存放，`wTotalLength` 由各段长度相加得出而不是手写常量，避免改描述符时忘记同步长度。字符串描述符需要包括索引 0 的语言 ID 数组，长度按 UTF-16 字节数计算。

SOF 与挂起处理影响功耗与恢复行为。挂起中断到来后应关闭不必要的外设时钟并降低核心频率，但要保留必要的唤醒源；支持远程唤醒的设备在挂起期间主动发唤醒信号前，要确认主机已在配置描述符中允许（`bmAttributes` 的远程唤醒位）并且主机驱动没有禁用该功能。用 SOF 中断做定时基准时要区分全速与高速的时基差异。

DMA 与双缓冲决定吞吐稳定性。端点级 DMA 可以让 CPU 在传输进行时处理其他事，但需要处理缓冲切换的临界区：主机可能在你读取状态寄存器的同时完成一次传输。双缓冲（一个缓冲在被主机取走时另一个继续接收）能显著降低高速批量传输的丢包概率，代价是每个端点占用两倍缓冲，以及固件必须正确地在两个缓冲之间切指针。如果控制器支持硬件自动切换，优先使用硬件机制而不是软件轮询。

## 4. 主机侧调试工具与判读

Windows 侧首选 USB Device Tree Viewer，它把设备描述符、配置描述符、接口与端点、电源需求、驱动绑定和错误码以树形展示，是判断"描述符是否被正确解析"的最快手段；设备管理器中的错误码（如 10、28、43）配合它使用能快速缩小范围。设备树工具看到的端口连接速度还能确认设备到底跑在 Full Speed 还是 High Speed，验证 chirp 握手是否成功。

Wireshark 配合 USBPcap（Windows）或 usbmon（Linux）可以抓到 URB 级与包级流量，枚举过程能看到每次控制传输的 SETUP 内容、数据长度和握手结果，是定位"哪一步失败"的决定性证据。抓包前先明确要看的是枚举还是运行期流量，运行期抓包量大、需要过滤到具体设备地址或端点。

Linux 侧用 `lsusb` 看设备与描述符概要（`lsusb -t` 看拓扑与速度，`lsusb -v` 看完整描述符），`usbmon` 抓包，`usbhid-dump` 直接读 HID 原始报表，配合 `dmesg` 里的枚举日志能看出驱动绑定与错误。`libusb` 用于在用户态写测试工具（免驱、跨平台），适合做 PC 侧的协议验证与产线测试。

Linux 还可以用 sysfs 观察设备状态：`/sys/bus/usb/devices/` 下每个设备目录包含 `speed`、`bMaxPower`、`idVendor`、`idProduct` 等节点，`/sys/kernel/debug/usb/` 下能看到主机控制器与端点状态。Windows 侧可以用 PowerShell 的 `Get-PnpDevice` 与 `Get-PnpDeviceProperty` 查看设备实例与驱动绑定状态，排查"驱动装了但没绑定"的情况无需安装额外工具。

判读抓包时先分清三类现象：控制传输失败（枚举阶段）看 SETUP 的 `bmRequestType` 与 `wLength` 是否符合预期、设备返回长度是否匹配；握手异常（运行期）看 NAK/STALL 在哪个端点上出现、是持续还是偶发；数据错误看 CRC 与 PID 校验失败的分布，若集中在插拔瞬间，多半是电源或接触问题而不是协议实现。抓包文件应连同设备树截图一起保存，便于对比"改前改后"的行为差异。

## 5. 时钟、电源与低功耗实现

USB 全速与高速对时钟精度的要求不同：全速设备可以使用内部 RC 振荡器，但精度必须满足规范要求，否则主机采样出错，表现为枚举偶尔成功、数据偶发错误；高速设备必须使用满足抖动的晶振或专用时钟源，许多控制器要求 48 MHz 时钟或由 PLL 从晶振倍频得到。用内部振荡器省成本时，务必查数据手册中 USB 模式对时钟精度的具体要求，并在全温度范围内实测。

供电方面，USB 供电设备在 VBUS 上升后需要一定稳定时间才能开始工作，固件不应在检测到 VBUS 的瞬间就初始化收发器。自供电设备要单独处理"仅外部供电"与"同时接了 USB"两种情形：前者不应出现任何 USB 活动，后者才启动 USB。带电池的设备还要考虑 USB 供电与电池供电的优先级，以及充电时是否会影响 USB 通信质量。

低功耗设计要结合挂起状态：总线挂起后关闭 USB 时钟与收发器通常能省下大部分电流，但要保留唤醒源与必要的 PHY 状态。若产品需要在挂起期间检测插入事件或按键唤醒，应当使用支持远程唤醒的配置，并确认主机已启用该功能。挂起电流是否达标必须实测，规范给出的上限（USB 2.0 设备 2.5 mA）在收发器未正确关闭时很容易超出。

## 6. 常见故障与排查顺序

枚举不稳定（设备反复出现与消失）通常先排查供电与线缆：总线供电设备在启动瞬间的浪涌是否把 VBUS 拉低、`bMaxPower` 是否申报过高、线缆与连接器接触是否可靠；其次看信号质量，最后才是固件时序。若设备树工具能看到设备但速度不对，优先怀疑 D+ 上拉与 chirp 时序。

CDC 丢数据分两类：主机侧串口软件没读、内部缓冲溢出（发送侧），或设备侧端点没有及时补包、接收缓冲溢出（接收侧）。改进顺序是先加大设备侧缓冲并实现流控（CDC 的 SET/GET_LINE_CODING 与串口控制信号可传递流控意图），再考虑提高轮询与包长，最后才排除 USB 层丢包。批量传输本身有重传，USB 层丢数据在正常硬件上很少见。

拔插后不恢复多半是设备状态机没有重新回到默认状态：固件在断开事件后应复位协议栈、清零地址与配置状态、重置端点缓冲与上层状态机。自供电设备额外需要检测 VBUS 而非只检测 USB 连接，因为自供电设备在只用外部电源时 D+ 上拉可能仍在，主机会看到"连接但错误"的设备，因此正确做法是把 VBUS 存在与否纳入连接状态判定。

Windows 驱动缓存导致的问题包括：改了 PID/VID 后仍匹配旧驱动（需卸载设备并清理驱动记录）、把同一 PID 的设备用于不同固件导致设备实例路径复用、以及序列号缺失使多个设备共用一个配置。发布前应固定 VID/PID 与序列号策略，避免在量产阶段改动。

HID 类问题常表现为"设备无法启动（代码 10）"或数据格式不对，根因多在报表描述符：usage page 与 usage 组合、report ID 与 report count 不匹配、逻辑最小值与最大值范围冲突。此时应先用 `usbhid-dump` 或主机侧 HID 工具验证原始字节，再对照报表描述符逐项核对。

## 7. 固件升级路径

DFU 是最通用的方案：设备实现 DFU 类接口，通过控制传输下载固件，主机侧用 dfu-util 或厂商工具驱动升级流程。DFU 1.1 支持运行时切换到 DFU 模式（设备在应用里主动跳转）与通过特定描述符声明升级能力；具体请求集与状态机以 USB-IF 的 DFU 规范为准。优点是免驱、跨平台，缺点是需要在应用中实现跳转逻辑，且升级期间设备功能不可用。

ROM bootloader 是最省固件的方案：芯片出厂固化的引导程序通过 USB 接收固件，只要在上电时让芯片进入该模式（具体方式以芯片数据手册为准，常见是引脚电平、按键或复位序列配合）。优点是固件损坏也能恢复，缺点是需要用户物理操作，且烧录速度与协议受厂商工具限制。

双区（A/B）升级把 Flash 分成两份，运行区收到新固件后校验并切换启动区，配合看门狗与启动计数器实现失败回滚；代价是固件空间减半、需要管理启动标志与版本。选择依据通常是现场可恢复性要求：完全无法接触设备的现场产品优先双区加回滚，开发板与可手动操作的产品用 DFU 或 ROM bootloader 更省事。

升级路径的实现细节（分区表、跳转向量表重定位、Flash 写入与擦除顺序）与具体芯片相关，见 [[04-Microcontrollers/00-README|微控制器]] 对应目录；协议侧的类和描述符见 [[05-Communication/05-USB协议/003-传输类型、端点与设备类|传输类型、端点与设备类]]，供电不足导致的枚举异常见 [[05-Communication/05-USB协议/005-USB供电与USB-PD|USB 供电与 USB-PD]]。
