# 传输类型、端点与设备类

USB 是主机主导的轮询总线：设备不能主动发送数据，只能把数据放进端点缓冲区等主机来取。端点的传输类型决定了主机多久来一次、一次能拿多少、丢包要不要重传。选错传输类型或把包大小算错，往往不是"性能差一点"，而是功能直接不成立（例如等时传输下的音频出现爆音、中断传输的自定义协议吞吐远低于预期）。

## 1. 四种传输类型对比

| 传输类型 | 方向 | 低速 | 全速包上限 | 高速包上限 | 带宽与延迟 | 重传 | 典型用途 |
|---|---|---|---|---|---|---|---|
| 控制 | OUT+IN（双向） | 8 B | 8/16/32/64 B | 64 B | 保证但不保证速率，延迟不确定 | 有 | 枚举、类请求、命令与状态 |
| 中断 | IN 或 OUT | 8 B | 64 B | 1024 B | 保证最大轮询周期，延迟有界 | 有 | HID、CDC 通知、按键与传感器小数据 |
| 批量 | IN 或 OUT | 不支持 | 8/16/32/64 B | 512 B | 不保证带宽与延迟，有空闲才走 | 有 | MSC、CDC 数据、大块传输 |
| 等时 | IN 或 OUT | 不支持 | 1023 B | 1024 B | 保证带宽，不保证数据正确 | 无 | UAC 音频、UVC 视频 |

等时传输在硬件层不做重传也不做 CRC 纠错，主机会照约定时间取走数据，出错就丢掉，所以必须靠上层缓冲与纠错容忍丢包；反过来，批量传输可以在错误的时机一直重试到成功，代价是延迟不可控。

## 2. 主机主导的轮询模型与帧结构

所有传输都由主机发起：主机发出令牌包（IN/OUT/SETUP）指明端点，设备在数据包中给出或接收内容，最后由握手包确认。批量传输由主机在每帧/微帧的周期性传输排完之后，用剩余时间安排；中断与等时则在每帧/微帧开始时按 `bInterval` 打开调度窗口。这解释了为什么"批量传输的实测吞吐"取决于总线负载，而"中断传输的实际延迟"由 `bInterval` 加协议开销决定。

时基方面，Full Speed 以 1 ms 为一帧，High Speed 以 125 µs 为一微帧。全速下 `bInterval` 直接是毫秒数（1、2、4……直至 255）；高速下该字段按 2 的幂解释，最小间隔对应 125 µs，因此高速中断端点的最高轮询频率是 8 kHz。使用 SOF 做时间基准的固件要注意 High Speed 下一个毫秒包含 8 个 SOF。

高带宽等时与中断端点在高速下允许一个微帧内安排多个事务，事务数在 `wMaxPacketSize` 的高 2 位编码，最多 3 个，因此单个等时端点每微帧的有效上限是 3 × 1024 B。是否使用它要结合主机控制器的调度能力，具体编码规则以 USB 2.0 规范第 9 章的端点描述符定义为准。

## 3. 端点 0 的特殊性

端点 0 是设备唯一必须实现的端点，只在控制传输上使用，不参与批量/中断/等时调度。它不受 `bEndpointAddress` 描述——方向由每次控制传输自行决定，设备侧由硬件或协议栈提供共享的 SETUP/DATA/STATUS 缓冲。

`bMaxPacketSize0` 由设备描述符申报，全速与高速设备通常为 64 B，低速设备只能是 8 B，取值必须是 8/16/32/64 之一。这个值在枚举第 3 步就要被主机读到（见 [[05-Communication/05-USB协议/002-描述符与枚举过程|描述符与枚举过程]]），所以固件必须在还未分配地址、甚至还未完成初始化时就以正确尺寸响应。

枚举成功后端点 0 仍然承担所有类请求与厂商请求，例如 CDC 的 SET_LINE_CODING、DFU 的下载命令。如果固件在某个类请求上返回 STALL 的时机不对，会同时影响枚举与运行时控制命令，这类问题在抓包时表现为控制传输的 STATUS 阶段失败。

## 4. 带宽与延迟的取舍

总线带宽不是按设备平均分配的。USB 2.0 为周期性传输（中断加等时）保留带宽上限，高速下每个微帧的周期性部分有明确占比限制，其余留给控制与批量；因此同时挂多个等时摄像头或音频接口时，先被挤压的是批量传输（U 盘读取速度骤降），而不是等时流本身。

工程核算顺序通常是：先按数据类型选传输类型，再按"每帧/微帧需要搬多少字节"反推 `wMaxPacketSize` 与 `bInterval`。例如一个全速 HID 端点每 1 ms 上报 64 字节，理论上限约 64 KB/s，做成 8 字节每 1 ms 就只有 8 KB/s；要把吞吐做到 1 MB/s 量级，全速批量端点每帧至少要凑到约 19 个满包（64 B）才够，且要接受随负载波动的实测结果。

延迟一侧的约束是调度周期：中断端点的最坏延迟约为 `bInterval` 加上若干包时间，等时端点还要考虑缓冲带来的额外延迟。音频这类对抖动敏感的应用宁可牺牲带宽也要固定周期，这也是 UAC 普遍使用等时传输的原因。

## 5. 设备类速查（含类代码）

| 类 | 类代码（Class/SubClass/Protocol） | 典型设备 | 主要传输类型 | 免驱程度 |
|---|---|---|---|---|
| CDC-ACM | 0x02 / 0x02 / 0x01 | 虚拟串口、调试口、串口桥 | 批量 + 中断通知 | Win10 起内置 usbser，旧系统需 INF |
| HID | 0x03 / 0x01 / 0x01 键盘、0x02 鼠标 | 键鼠、自定义小数据 | 中断 | 高，各系统自带 |
| MSC | 0x08 / 0x06 / 0x50 | U 盘、读卡器、固件交换盘 | 批量 | 高 |
| UAC（音频） | 0x01 | 声卡、USB 麦克风 | 等时 + 中断 | 高，UAC1 兼容性更好 |
| UVC（视频） | 0x0E | 摄像头 | 等时（或批量） | 高 |
| DFU | 0xFE / 0x01 / 0x02 | 固件升级 | 控制（少量类请求） | 中，需 dfu-util 或厂商工具 |
| CDC-ECM | 0x02 / 0x06 / 0x00 | USB 网卡 | 批量 + 中断通知 | Linux/macOS 免驱 |
| RNDIS | 0x02 / 0x02 / 0xFF（厂商子协议） | USB 网卡（Windows 向） | 批量 + 中断通知 | Windows 侧常见，其他系统需驱动 |
| MTP / PTP | 0x06 / 0x01 / 0x01 | 手机、相机 | 批量 | 中，依赖系统组件 |

类代码的权威取值以 USB-IF 的 Class Codes 文档为准；`bInterfaceSubClass` 与 `bInterfaceProtocol` 写错时，系统仍会加载类驱动但随后报错，这类问题很难从设备日志看出，必须用抓包或设备树工具核对。

## 6. CDC 与 HID 的工程选择

HID 的最大优势是免驱：Windows、Linux、macOS 都自带 HID 驱动，插上即可通信，不需要 INF、不需要管理员权限，出厂设备无需签名。代价是报文语义被绑定在 HID 报表描述符上——主机按报表描述符解释数据，固件不能用任意字节流；中断端点每帧/微帧只能传一个包，全速下 64 字节封顶，即约 64 KB/s 量级；HID 还带有"报表协议"与"引导协议"两套模式，键盘鼠标需要同时实现引导协议才能在 BIOS 阶段可用。

CDC-ACM 表现为普通串口，天然支持流量控制、波特率等线路状态（虽然虚拟串口下波特率通常不影响实际速率，但主机侧软件往往要求能设置），吞吐可做到每秒数百 KB 到 MB 级。代价是驱动依赖：Windows 10 之前需要 INF 或厂商驱动，不同系统的设备节点命名不同（COMx、/dev/ttyACMx），直接面向最终用户的产品要评估安装体验。

选择建议可以概括为三条：数据量小、要求零安装、可以接受自定义报表语义，选 HID；数据量大、需要流式收发与流控、目标机器可控，选 CDC-ACM；两者都不满足（大容量存储、音频、视频、网络）直接选对应标准类，不要用自定义协议重造类驱动。

## 7. PID/VID 与驱动匹配

系统加载驱动的顺序大致是：先看接口的类/子类/协议是否匹配系统自带的类驱动，再按 VID/PID（以及设备序列号）匹配 INF 或厂商驱动，最后才是设备级类代码。因此同一个 USB 设备可以被拆成多个接口分别绑定不同驱动（复合设备），例如一个音频接口加一个 HID 接口。

调试期频繁改 PID 是常见做法，但要注意三个坑：Windows 会按 VID/PID/序列号缓存驱动绑定与设备实例，改了 PID 后旧记录仍可能命中，需要清理设备缓存或换序列号；如果设备本来能匹配系统类驱动，改 PID 只是让它匹配到一个 INF 不存在的条目，反而变成"未知设备"；用自定义 PID 发布的产品仍需要合法 VID，不能直接借用厂商样例里的 VID，量产前应向 USB-IF 申请。

一个设备声明多个配置、或一个接口声明多个备用设置时，驱动匹配的是接口层描述符，切换配置与备用设置的逻辑要在固件里实现，见 [[05-Communication/05-USB协议/002-描述符与枚举过程|描述符与枚举过程]]。

## 8. 复合设备与接口关联

一个 USB 设备可以同时提供多个功能，实现方式有两种。第一种是复合设备：用一个配置下的多个接口分别绑定各自的类驱动，每个接口独立拥有类/子类/协议与端点，系统会把它识别成多个设备节点（例如一个麦克风加一个 HID 按键）。第二种是用接口关联描述符（IAD）把两个接口声明为同一个功能（常见于 UAC 的音频控制接口与音频流接口），这样系统才会把它们当作一个音频设备处理，否则会出现"两个音频设备、其中一个无法使用"的现象。

多接口设计的约束在于端点与带宽的共享：所有接口共用控制端点 0 与总线带宽，一个接口的等时流会挤压同一总线上其他设备的批量传输。设备侧则要保证每个接口的端点号不冲突、配置描述符集合完整且 `wTotalLength` 正确，否则主机可能只识别出部分接口。量产设备还要考虑枚举时间：接口与字符串越多，枚举所需控制传输越多，接在慢速 Hub 后面时更容易超时。

## 9. 端点的 Halt、NAK 与错误处理

端点握手结果有明确语义。ACK 表示数据已被正确接收；NAK 表示设备暂时无法响应（缓冲未就绪、没有数据可取），主机稍后重试，这是正常的流控手段而不是错误；STALL 表示端点被 Halt 或请求不被支持，主机必须通过 CLEAR_FEATURE(ENDPOINT_HALT) 才能恢复；高流量批量端点还会返回 NYET 表示上一包已被接受但暂时不要再发，用于高速批量传输的流控。

固件常见的错误是在缓冲未就绪时回 STALL 而不是 NAK，结果主机把端点标记为 Halt 并停止收发，上层表现为"通信突然中断且不再恢复"。正确做法是：缓冲未准备好回 NAK；协议层确实要拒绝一个非法请求时才回 STALL；并在需要时实现主机发起的 CLEAR_FEATURE 处理。

批量与中断端点还有数据翻转（DATA0/DATA1）机制：双方各维护一个翻转位，收到期望序号的包才接受，重复包被丢弃并重发 ACK。调试中"数据偶发丢失或重复"往往与端点复位后翻转位未同步有关，标准的恢复手段是对端点执行 Set/Clear Halt 让翻转位重新同步，而不是靠上层重传掩盖。

## 10. 端点资源与缓冲规划

MCU 侧的端点数量与缓冲总量是硬约束。规划顺序是：先列出每个接口需要的中断与批量端点，按最大包长乘以缓冲包数（单缓冲、双缓冲）相加，再与控制器可用的 USB RAM 比较。全速控制器通常只有几百字节的端点 RAM，做复合设备（CDC + HID + MSC）时经常需要缩减包长或改用单缓冲。

高速批量端点若只配单缓冲，在主机连续调度时会因为缓冲切换延迟而插入 NAK，实测吞吐明显低于理论值；双缓冲能显著改善但占用双倍 RAM。中断端点则相反，包长小、周期长，单缓冲通常足够。等时端点对缓冲的要求最高，因为不能重传，需要用双缓冲平滑主机的调度抖动。

端点数量的另一个约束来自描述符：接口声明的端点数量必须与实际实现的端点一致，多声明会让主机按不存在的端点调度，表现为传输超时或驱动加载失败。
