# Modbus 软件实现

RS-485 上的 Modbus 软件要处理四件硬件不替你做好的事：准确定帧、可靠校验、精确的方向切换、以及主站的调度与超时。这四项里任何一项做错，现象都是"偶发通信失败"，很难从协议层面看出来。

## 1. 方向切换时序

半双工收发器在同一对线上分时收发，方向控制由软件负责。最典型的错误是**在数据还没发完时关闭驱动器**：

```c
/* 不安全的写法：发送函数返回不代表最后一个字节已经离开移位寄存器 */
void rs485_send_bad(uint8_t *data, uint16_t len)
{
    HAL_GPIO_WritePin(DE_GPIO_Port, DE_Pin, GPIO_PIN_SET);
    HAL_UART_Transmit(&huart2, data, len, 100);
    HAL_GPIO_WritePin(DE_GPIO_Port, DE_Pin, GPIO_PIN_RESET);  /* 可能截断末字节 */
}

/* 正确写法：等发送完成标志（TC），而不是等发送缓冲空（TXE） */
void rs485_send(uint8_t *data, uint16_t len)
{
    HAL_GPIO_WritePin(DE_GPIO_Port, DE_Pin, GPIO_PIN_SET);
    HAL_UART_Transmit(&huart2, data, len, 100);
    while (__HAL_UART_GET_FLAG(&huart2, UART_FLAG_TC) == RESET) {
        /* 等待最后一个字节完全移出 */
    }
    HAL_GPIO_WritePin(DE_GPIO_Port, DE_Pin, GPIO_PIN_RESET);
}
```

要点：

- `TXE`（发送数据寄存器空）只表示可以写入下一个字节，最后一个字节可能还在移位寄存器里；必须等 `TC`（发送完成）。
- 用 DMA 发送时，DMA 传输完成中断也**不等于**最后一个字节已上线，仍需等待 `TC` 标志或 UART 的发送完成回调。
- 关闭驱动器后应留出少量延时再打开接收，给总线电平稳定时间；具体延时与波特率和收发器有关，通常按 1~2 个字符时间留。
- 如果 MCU 的收发器带自动方向控制，或使用了支持 RS-485 模式的 UART（由硬件自动控制 DE），可以省掉这一层，但要确认其支持的波特率范围。

## 2. CRC-16 计算

Modbus RTU 使用 CRC-16，多项式 0xA001（反向表示的 0x8005），初始值 0xFFFF，发送时**低字节在前**。

```c
uint16_t modbus_crc(uint8_t *buf, uint16_t len)
{
    uint16_t crc = 0xFFFF;
    for (uint16_t i = 0; i < len; i++) {
        crc ^= buf[i];
        for (uint8_t j = 0; j < 8; j++) {
            if (crc & 0x0001) {
                crc = (crc >> 1) ^ 0xA001;
            } else {
                crc >>= 1;
            }
        }
    }
    return crc;
}
```

实现时的常见错误：

- **字节序**：把 CRC 按高字节在前发送，导致所有帧都被对端判为校验错。发送时应 `buf[n] = crc & 0xFF; buf[n+1] = crc >> 8;`。
- **校验范围**：CRC 计算包含从站地址和功能码，不包含 CRC 自身。
- **用错多项式**：Modbus 用的是 0xA001，与其他协议（如 CRC-16/CCITT）不同，直接复用现成库时要核对参数。

对性能敏感的实现可以用查表法（256 项表）替代逐位循环，代价是占用 512 字节 Flash。

## 3. 帧分界

RTU 靠时间分界，实现方式有三种，各有取舍：

| 方式 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 定时器轮询 | 每收到一个字节就重置一个定时器，超时则认为帧结束 | 实现简单 | 需要精确定时器；高速率下超时很短，易受中断抖动影响 |
| UART 空闲中断 | 总线空闲超过一个字符时间触发中断，标志帧结束 | 硬件判定，精度好 | 需要 MCU 支持空闲检测；空闲阈值固定，需与波特率匹配 |
| 固定长度 + 超时 | 按功能码推断期望长度，收满即结束 | 效率高 | 异常响应、广播、不同功能码长度不同，易错 |

工程上推荐**空闲中断（或空闲检测 + DMA）**，配合一个兜底超时。DMA + 空闲中断的组合可以把接收完全交给硬件，中断只在帧结束时触发一次，CPU 开销最低。

帧分界还有一个容易忽略的细节：**接收缓冲区要能容纳最长帧**。RTU 的 PDU 最大 253 字节，加上地址和 CRC 共 256 字节。按 8 字节接收缓冲去实现，遇到对端返回大块数据时会直接溢出，表现为"读多个寄存器时数据错乱"。

## 4. 主站轮询调度

Modbus 主站的核心是一个轮询循环。设计要点：

- **请求-响应严格串行**。总线上同一时刻只能有一个主站和一个请求，必须收到响应（或超时）后才能发下一个请求。
- **超时时间要按波特率和最长响应帧长度计算**。经验公式是"帧传输时间 × 2 + 从站处理时间"，并留出余量。超时设得过短会误判重试，反而加剧总线拥塞。
- **重试策略要有限**。通常重试 1~2 次，连续失败则标记该从站离线并降低其轮询优先级，避免一个故障从站拖垮整个轮询周期。
- **轮询周期要能算出来**：所有从站的请求帧时间 + 响应帧时间 + 3.5 字符静默间隔之和，就是完整一轮的最小时间。这个数字决定系统能提供的刷新率。

一个简化的轮询周期估算：

$$
T_{cycle} \approx \sum_{i} \left( \frac{(N_{req,i} + N_{rsp,i}) \times 10}{B} + T_{gap} + T_{proc,i} \right)
$$

其中 $N$ 是以字节计的帧长（按每字节 10 位计），$B$ 是波特率，$T_{gap}$ 是 3.5 字符静默间隔，$T_{proc}$ 是从站处理时间。

举例：8 个从站，每个请求 8 字节、响应 20 字节，115200 bps，静默间隔约 0.3 ms，从站处理 2 ms：

$$
T_{cycle} \approx 8 \times \left( \frac{28 \times 10}{115200} + 0.0003 + 0.002 \right) \approx 8 \times 4.7\ \mathrm{ms} \approx 38\ \mathrm{ms}
$$

即刷新率约 26 Hz。如果控制回路需要 20 ms 周期，这个配置就不够，只能减少从站数量、减少每次读取的寄存器数，或提高波特率。

- **分块读取**：需要读的寄存器尽量合并成一次请求，减少帧数和静默间隔开销；但单次请求不要接近 125 个寄存器的上限，留出余量。
- **按优先级分配**：把关键数据（报警、状态）安排在轮询周期的前半段，非关键数据（统计、配置）放慢。

## 5. 从站实现

从站的处理流程相对简单，但有几个必须做对的点：

1. **地址过滤**：只处理广播和自己的地址，其他帧静默丢弃。
2. **校验先行**：CRC 校验失败直接丢弃，不响应（规范要求从站在校验错误时不响应）。
3. **功能码与地址范围检查**：不支持的功能码返回 0x01，地址越界返回 0x02，数量超限返回 0x03。
4. **及时响应**：从站必须在主站超时前完成响应。长耗时操作（如需要采样、写 Flash）应返回 0x05（确认）或 0x06（忙），而不是让主站等到超时。
5. **响应帧长度正确**：读操作返回"字节数 + 数据"，字节数是数据部分的字节数，不含功能码和字节数本身。这一处实现错误会导致对端解析错位。
6. **不主动发送**。从站不应在收到请求前占用总线，否则会与主站的请求冲突。

从站的状态机通常不需要复杂设计，因为每个请求都是独立的。唯一需要保存的状态是"当前是否正在响应"和"上一条请求的处理结果"，用于实现 0x05/0x06 的延迟响应语义。

## 6. 超时、重试与去重

- **超时判定**要区分"完全没有响应"和"响应校验错"。前者指向地址错误、从站离线、接线问题；后者指向干扰、波特率偏差或从站实现问题。
- **重试前要确认操作幂等性**。读操作可以无条件重试；写操作（尤其是 0x06/0x10 写寄存器）如果第一次实际已经执行成功只是响应丢失，重试会重复写入。对多数配置寄存器这类写入是幂等的（写同样的值），但对"累加""切换"这类操作就不是，需要在协议层设计去重或改用可读回校验的方式。
- **错误统计要保留**：按从站统计超时次数、校验错误次数、异常响应码，是现场定位问题最有效的数据。

## 7. 调试与自测

| 手段 | 用途 |
|---|---|
| USB 转 RS-485 模块 + Modbus 调试软件 | PC 侧模拟主站/从站，验证对端行为 |
| 逻辑分析仪 | 观察请求与响应的时序间隔、方向切换是否截断数据 |
| 串口助手（HEX 模式） | 手工构造报文，验证边界情况（越界地址、超限数量） |
| 错误计数与日志 | 长期运行统计，定位偶发问题 |

自测建议覆盖以下场景：地址越界、数量超限、不支持的功能码、CRC 错误、广播写入、长响应帧、从站不响应时的超时与重试、总线上有第三方设备时的地址干扰。
