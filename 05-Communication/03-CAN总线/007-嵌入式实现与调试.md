# 嵌入式实现与调试

CAN 控制器把链路层的复杂度都封装在硬件里：仲裁、位填充、CRC、应答、自动重发都不需要软件参与。软件要做的只有四件事——配置位时序、设置验收滤波、管理发送与接收缓冲、处理错误状态。剩下的工作量几乎全在"怎么组织周期报文的发送"和"总线出问题时怎么定位"上。

## 1. 控制器架构与能力差异

MCU 上的 CAN 控制器大致分三代：

| 类型 | 特点 | 代表 |
|---|---|---|
| 基本控制器 + 外部收发器 | 单/双接收缓冲、有限滤波器 | 早期 8 位与 16 位 MCU 内置控制器 |
| 带邮箱/多缓冲的经典控制器 | 多个发送邮箱、接收 FIFO、可编程验收滤波 | 多数 Cortex-M 的 bxCAN 类控制器 |
| 支持 FD 的控制器 | 双位时序、消息 RAM、TT 触发、时间戳 | 新一代汽车与工业 MCU 的 FDCAN 类控制器 |

选择时要核对的能力项：支持的帧格式（标准/扩展/FD）、**验收滤波器的数量和类型**（列表模式与掩码模式、是否可按 FIFO 分配）、发送邮箱数量、接收 FIFO 深度与溢出行为、是否支持自动重发、是否可关闭自动重发（用于一次性发送或时间触发通信）、是否有硬件时间戳（做时间同步或精确延迟测量时需要）、接收滤波是否覆盖扩展帧的全部 29 位。

**验收滤波器**是节点数较多时最容易出问题的地方。滤波器数量和通过模式的组合是有限的，节点需要接收的 ID 越多、越分散，就越容易超出硬件资源，只能退化成"全部通过 + 软件过滤"。软件过滤会让中断频率随总线负载线性上升，在高负载总线上直接影响实时性。设计初期就应统计每个节点需要接收的 ID 数量，并确认滤波资源够用。

## 2. 收发器选型与接口

MCU 的 CAN 控制器只处理数字逻辑，物理层由收发器完成。选型时核对以下项目：

| 项目 | 为什么重要 |
|---|---|
| 供电电压与逻辑电平 | 收发器可能是 5 V 供电而 MCU 为 3.3 V，逻辑侧兼容性需确认 |
| 最高速率与环路延迟 | 决定能否支持 CAN FD 的数据段速率 |
| 位对称性与传播延迟容差 | 高速率下直接影响采样裕量 |
| 待机/睡眠模式与唤醒方式 | 低功耗节点需要收发器支持总线唤醒 |
| 显性超时保护 | 防止软件异常时长拉低总线锁死网络 |
| 隔离能力 | 跨机柜、长线或有地电位差时必需 |
| 共模范围 | 决定能容忍多大的地电位差 |

一些经典的器件类别和它们的定位：经典 5 V 高速收发器（成本敏感、生态成熟）、3.3 V 兼容型（现代 MCU）、带待机与唤醒的型号（车身节点）、支持 FD 的型号（高数据段速率）、隔离型（工业现场）。具体型号的电压、速率与延迟指标以数据手册为准，不能凭型号代际推断。

**隔离方案**需要同时隔离信号与电源：数字隔离器或光耦负责 TXD/RXD 与使能信号，隔离 DC-DC 为总线侧供电。设计要点是隔离器件的传播延迟要对称，否则会破坏位时序；隔离电源的纹波和启动时间也要满足上电时序要求。具体选型见 [[07-Power-Management/00-README|电源管理]]。

## 3. 驱动结构

一个可维护的 CAN 驱动通常分成三层：

- **控制器驱动层**：时钟与引脚使能、位时序配置、滤波器配置、中断注册与状态查询。这一层只依赖 MCU，不包含业务语义。
- **收发管理层**：发送队列、周期报文调度、接收分发、错误状态监控与恢复。这一层把"帧"翻译成"消息"。
- **应用层**：消息编解码、状态机、与高层协议（CANopen/J1939/UDS）的对接。

**发送路径**的设计要点：

- 不要把长周期发送放在主循环里直接调用阻塞式发送。用发送队列 + 定时触发，让总线忙时排队而不阻塞其他任务。
- 明确队列满时的策略：丢弃旧帧、丢弃新帧，还是记录错误。周期状态报文通常选"丢旧保新"（最新状态更有价值），事件型报文必须记录丢弃并重试。
- 每次发送请求要有完成通知，用于统计发送失败率和检测总线关闭。

**接收路径**的设计要点：

- 中断里只做取帧和入队，解析放到任务上下文，避免长中断影响其他外设。
- 接收 FIFO 溢出是隐蔽的故障源：溢出后控制器会丢弃帧，只置位一个溢出标志。必须轮询或中断处理该标志并记录计数，否则现场表现为"偶发丢数据"而查不到原因。
- 帧的时间戳（若硬件支持）应随帧一起入队，用于分析延迟和抖动。

**错误状态处理**：定期（或在中断中）读取错误计数器和状态位，记录错误帧计数、被动错误与总线关闭事件。进入总线关闭后不要简单地无限自动恢复，至少要记录发生次数和发生时刻，否则会掩盖接线或终端问题。

## 4. 位时序配置的验证

配置完位时序必须验证，不能只看环回测试通过。验证步骤：

1. 用示波器测量一位的实际宽度，与目标波特率对比（例如 500 kbps 应为 2 μs）。
2. 用 CAN 分析仪确认帧能被稳定解码，观察错误计数是否保持为零。
3. 在总线两端各放一个节点交替发送，确认双向通信都正常（单节点自发自收不能暴露位时序偏差）。
4. 温度循环或长时间运行测试，暴露晶振漂移引起的问题。

计算方法与实例见 [[05-Communication/03-CAN总线/005-位时序与同步|位时序与同步]]。

## 5. 总线负载率与实时性核算

总线负载率是决定系统能否长期稳定运行的核心指标：

$$
\text{负载率} = \frac{\sum_i (N_i \times f_i)}{B}
$$

其中 $N_i$ 是第 $i$ 类帧的位数（含固定开销与位填充余量），$f_i$ 是发送频率，$B$ 是波特率。

工程建议：

- 设计目标控制在 **30%~50%** 以下，留出诊断、刷写和突发事件的余量。
- 计算时把位填充算进去，最坏情况按"每 5 位填充 1 位"估算（位数 × 1.2）。
- 单独核算**最坏延迟**：某个高优先级帧在总线最忙时刻的等待时间。低优先级帧在负载率超过 50% 后延迟会急剧增长。
- 预留诊断与刷写通道的带宽，UDS 刷写会长时间占满总线。

计算示例和帧位数表见 [[05-Communication/03-CAN总线/002-帧格式详解|帧格式详解]]。

## 6. 调试手段

| 工具 | 用途 | 判读要点 |
|---|---|---|
| USB-CAN 分析仪 | 抓帧、发送自定义帧、统计负载率 | 确认波特率与实际配置一致；观察错误帧计数 |
| 逻辑分析仪（带 CAN 解码） | 看单节点 TXD/RXD 波形与总线电平 | 区分"控制器没发"和"发了但总线上没有" |
| 示波器 | 看差分波形、显性位幅度、振铃、位宽 | 显性位振铃说明终端或拓扑有问题 |
| 万用表 | 断电测差分电阻 | 正常约 60 Ω，用于确认终端数量 |
| 协议分析软件 | 高层协议解码（CANopen/J1939/UDS） | 核对报文语义与状态机 |

**分层定位的顺序**：

1. 先确认控制器是否真的在发送——用示波器或逻辑分析仪看 TXD 引脚。
2. TXD 有波形但总线上没有 → 收发器供电、使能、隔离电源或收发器损坏。
3. 总线上有波形但分析仪报错误帧 → 波特率、采样点、终端电阻、总线长度。
4. 波特率正确但只有一个节点能通信 → 滤波器配置、收发器方向、该节点支线过长。
5. 通信正常但偶发丢帧 → 接收 FIFO 溢出、中断被长任务阻塞、总线负载率过高。
6. 一段时间后节点离线 → 错误计数器累加进入被动错误或总线关闭，检查终端、干扰源和地电位差。

## 7. 常见故障与现场排查表

| 现象 | 常见根因 | 处理方向 |
|---|---|---|
| 全网络不通 | 终端电阻缺失、总线短路、所有节点波特率不一致 | 断电测电阻、逐段断开定位 |
| 某节点始终不发 | 控制器未进入正常模式、TXD 引脚复用错误、收发器待机引脚状态错误 | 查引脚复用与初始化顺序 |
| 偶发错误帧且随线缆移动变化 | 接插件接触不良、支线过长、屏蔽层接地不当 | 检查接插件与屏蔽单点接地 |
| 提高速率后通信失败 | 采样点不一致、总线过长、收发器延迟不满足 | 统一采样点、缩短总线或降速 |
| 设备启停时通信中断 | 干扰耦合、地电位差、缺少隔离 | 加 TVS 与共模电感、改用隔离方案 |
| 上电顺序不同导致总线锁死 | 某节点在异常状态下持续输出显性 | 启用显性超时保护、检查收发器使能时序 |
| 长时间运行后掉线 | 错误计数累积、总线关闭后未正确恢复 | 记录并分析错误计数与恢复事件 |

## 8. 集成与验收清单

1. 位时序已用示波器实测验证，采样点与其他节点一致。
2. ID 分配有书面矩阵，新增节点在矩阵中登记。
3. 总线负载率已计算，并在最忙工况下实测（含位填充）。
4. 各节点的验收滤波器配置已核对，确认不会漏收或误收。
5. 接收 FIFO 溢出、总线关闭、错误计数等异常都有记录手段。
6. 终端电阻数量与阻值确认无误，拓扑为总线型。
7. 长线、跨机柜或强干扰场合已评估隔离方案。
8. 刷写与诊断流程已验证，并与正常通信的带宽安排协调。
