# 高层协议：CANopen / J1939 / UDS

裸 CAN 只定义了"怎么把 8 字节安全地送到总线上"，没有定义这 8 字节里放什么、怎么描述一个设备有哪些参数、怎么建立连接、怎么做固件升级。两个都"符合 CAN 规范"的设备直接对接，通常一个字都对不上。高层协议就是补上这一层约定，代价是引入各自的模型、状态机和工具链。

## 1. 为什么需要高层协议

只靠自定义 CAN 报文做设备互联，会遇到四个反复出现的问题：

- **互操作性**：不同厂家对同一个 ID 的数据定义不同，集成时需要逐个对接。
- **参数访问**：读一个参数、写一个参数、读一段配置，都没有统一的寻址方式。
- **网络管理**：节点如何启动、如何被监控、掉线如何检测。
- **诊断与升级**：故障码怎么读、固件怎么刷、标定怎么做。

三种主流协议对这四个问题的答案不同，适用的行业也不同。

## 2. CANopen

CANopen 由 CiA（CAN in Automation）制定，核心规范是 CiA 301（应用层与通信规范），面向工业控制、伺服驱动、机器人、电梯等场景。

**对象字典（Object Dictionary）**是 CANopen 的核心抽象。每个设备把所有可访问的参数组织成一张表，用 16 位索引 + 8 位子索引寻址（例如 0x6040:00 是控制字）。对象字典的语义是标准化的，因此一个 CANopen 主站不需要知道从站的具体实现，就能读写标准对象。

规范的通信对象包括：

| 对象 | 作用 | 默认 COB-ID（11 位 ID） |
|---|---|---|
| NMT | 网络管理：启动、停止、复位节点 | 0x000 |
| SYNC | 周期性同步信号，用于同步 PDO | 0x080 |
| EMCY | 紧急报文，上报故障码 | 0x080 + 节点号 |
| TIME | 时间戳广播 | 0x100 |
| PDO（TPDO/RPDO） | 过程数据，无协议开销的实时传输 | 按配置 |
| SDO | 服务数据，用于读写对象字典，有应答 | 0x600 + 节点号 / 0x580 + 节点号 |

**PDO 与 SDO 的分工**是 CANopen 设计的关键：

- PDO 用于周期性实时数据，一帧可以承载多个映射的信号，无额外协议头，效率高，但需要预先配置映射关系，且默认是"广播式"的无确认传输。同步 PDO 由 SYNC 触发，保证采样时刻一致。
- SDO 用于参数读写，有请求-应答和分段传输，适合大块数据和初始化阶段的配置，实时性差。

节点状态机（初始化 → 预运行 → 运行 → 停止）决定了哪些通信对象可用：预运行状态下只有 SDO 和 NMT 可用，进入运行态后才启用 PDO。这个设计让设备可以先被配置好再投入实时通信。

CANopen 的 ID 由功能码 + 节点号构成，11 位 ID 被划分成固定的服务段，因此节点数受节点号位数限制（通常 1~127）。CANopen FD（CiA 1301）扩展到了 FD 帧，但存量设备以经典 CAN 为主。

## 3. J1939

SAE J1939 是商用车和重型机械的应用层标准，覆盖卡车、客车、农机、船舶、发电机组。

J1939 使用 29 位扩展 ID，把它划分成几个字段：

| 字段 | 位数 | 含义 |
|---|---|---|
| 优先级 | 3 | 数值越小优先级越高，默认多为 6 |
| 保留/数据页 | 2 | 扩展参数组编号的数据页 |
| PDU 格式（PF） | 8 | 决定报文是点对点还是广播 |
| PDU 特定（PS） | 8 | PF < 240 时为目的地地址；PF ≥ 240 时为组扩展 |
| 源地址 | 8 | 发送节点的地址 |

**参数组编号（PGN）**由数据页、PF 和（当 PF ≥ 240 时）PS 组成，用来标识一组参数。例如发动机转速、车速、冷却液温度都是标准化的 PGN，各自规定了数据长度、分辨率和偏移量。这套标准化参数定义（SPN）让不同厂家的发动机和仪表可以直接互通。

J1939 还定义了地址声明流程（通过 NAME 和地址声明报文解决地址冲突）、请求报文（向某个 PGN 请求数据）、传输协议（TP.CM/TP.DT，用于传输超过 8 字节的数据块）以及诊断报文（DM1/DM2 等故障码广播）。

J1939 的实际复杂度主要来自庞大的参数集和厂商扩展。做项目时通常只实现需要的那部分 PGN 和 SPN，并保留一份参数对照表。

## 4. UDS（统一诊断服务）

UDS 由 ISO 14229 定义，是汽车诊断的通用应用层协议，用于读取故障码、读写数据、执行例程、刷写固件、安全访问。

**传输层**：UDS 报文常常超过经典 CAN 的 8 字节，需要 ISO-TP（ISO 15765-2）做分段与重组。ISO-TP 用首帧、连续帧、流控帧实现分片传输，并定义了块大小和最小间隔时间两个流控参数。诊断的实时性通常不是关键，因此 ISO-TP 的配置重点是正确性而非性能。

**服务与响应格式**：请求的服务 ID 和响应之间有固定关系——肯定响应为服务 ID + 0x40，否定响应固定为 0x7F + 服务 ID + 否定响应码（NRC）。常用服务包括：

| 服务 | 名称 | 典型用途 |
|---|---|---|
| 0x10 | 诊断会话控制 | 切换到编程会话、扩展会话 |
| 0x11 | ECU 复位 | 复位后生效的配置 |
| 0x14 | 清除诊断信息 | 清除故障码 |
| 0x19 | 读取诊断信息 | 读取 DTC 及状态位 |
| 0x22 / 0x2E | 按标识符读/写数据 | 读写标定与配置数据 |
| 0x27 | 安全访问 | 种子-密钥挑战，解锁受保护操作 |
| 0x28 | 通信控制 | 关闭正常报文发送，刷写时使用 |
| 0x31 | 例程控制 | 触发自检、擦除 Flash |
| 0x34 / 0x36 / 0x37 | 请求下载 / 传输数据 / 请求退出传输 | 固件刷写 |

**否定响应码**是诊断排查中信息量最大的部分，常见的有服务不支持、子功能不支持、报文长度或格式错误、条件不满足、请求超出范围、安全访问被拒绝、需要先响应（0x78，表示处理中需要更多时间）。读出 NRC 基本就能定位是会话状态、安全等级还是参数范围的问题。

**诊断寻址**：经典做法是用两个 ID 分别作为物理请求和响应，另有功能寻址 ID 用于广播请求。具体 ID 分配由整车厂的诊断规范定义，不同车型不同，不能假定通用值。CAN FD 出现后，诊断报文可以直接承载更长的数据，ISO-TP 的分段压力下降。

## 5. 三者对比与选择

| 维度 | CANopen | J1939 | UDS |
|---|---|---|---|
| 主要行业 | 工业控制、伺服、机器人 | 商用车、农机、船舶 | 汽车诊断与刷写 |
| ID 长度 | 11 位（也有 FD 版本） | 29 位 | 取决于底层，通常 11 位 |
| 数据模型 | 对象字典（索引 + 子索引） | PGN / SPN | 数据标识符 + 服务 |
| 实时数据机制 | PDO（可同步） | 周期广播 PGN | 不以实时数据为主 |
| 配置与参数 | SDO | 请求报文 + 传输协议 | 0x22 / 0x2E |
| 网络管理 | NMT + 心跳/节点保护 | 地址声明 | 会话与安全等级 |
| 典型工具 | CANopen 主站、EDS 编辑器 | J1939 分析仪、DBC | 诊断仪、ODX/PDX 数据库 |

选择原则很直接：工业设备互联选 CANopen；商用车或需要标准化参数集选 J1939；做 ECU 的诊断、标定和 OTA 刷写选 UDS。实际项目里常见的是组合：一个 ECU 内部用 UDS 做诊断和刷写，运行时用自定义或 CANopen/J1939 报文做过程数据——这也是为什么"CAN 应用层"往往需要同时实现两套东西。

## 6. 实现与调试要点

- **不要自己发明参数寻址**。如果目标行业已有标准，跟随标准能直接复用工具链和客户经验。
- **ID 规划要在项目初期完成**。三种协议都会占用特定 ID 段，随意分配会在集成阶段产生冲突。
- **诊断与实时数据要分开规划带宽**。刷写过程会长时间占满总线，此时正常报文应当被抑制（UDS 0x28 服务的作用），否则刷写会失败或影响整车功能。
- **保留一份可维护的通信矩阵**（DBC、EDS 或 ODX 文件）。手工维护 Excel 表格在节点数增加后必然失控。
- **协议一致性测试**：CANopen 有 CiA 的一致性测试，J1939 和 UDS 也有各自的测试规范。自测通过不代表能通过集成测试，尤其是在超时、流控和异常响应路径上。
