# 帧格式详解

CAN 只有四种帧类型，全部结构紧凑：数据帧最多 8 字节（CAN FD 为 64 字节），其余是固定格式的控制位。理解帧格式的意义在于两件事：一是能算出总线负载率，二是能在逻辑分析仪上逐字段核对异常帧。

## 1. 数据帧的逐字段结构

标准数据帧（CAN 2.0A）按顺序由七个场组成：

| 场 | 长度 | 内容 | 作用 |
|---|---|---|---|
| SOF 帧起始 | 1 位显性 | 0 | 标志帧开始，用于硬同步 |
| 仲裁场 | 12 位 | 11 位 ID + RTR | 标识内容并决定优先级 |
| 控制场 | 6 位 | IDE + r0 + 4 位 DLC | 区分帧格式并声明数据长度 |
| 数据场 | 0 ~ 64 位 | 0 ~ 8 字节数据 | 有效载荷 |
| CRC 场 | 16 位 | 15 位 CRC + 1 位隐性定界符 | 差错检测 |
| ACK 场 | 2 位 | ACK 槽 + 隐性定界符 | 确认接收 |
| EOF 帧结束 | 7 位隐性 | 全 1 | 标志帧结束 |

各字段的工程含义：

- **ID**：11 位，数值越小优先级越高（见 [[05-Communication/03-CAN总线/001-总线模型与仲裁机制|总线模型与仲裁机制]]）。
- **RTR**：显性表示数据帧，隐性表示远程帧。
- **IDE**：显性表示标准帧，隐性表示扩展帧。
- **r0**：保留位，发送时固定为显性。
- **DLC**：4 位，取值 0~8 表示数据字节数。经典 CAN 中 DLC 大于 8 时按 8 处理；CAN FD 中 DLC 的编码被重新定义以表示 12~64 字节。
- **CRC**：15 位，覆盖 SOF 到数据场的全部内容。接收方计算不一致时在 CRC 定界符后发出错误帧。
- **ACK 槽**：发送方发隐性位，任何正确接收该帧的节点在此位置发显性位。发送方读到显性即认为发送成功。
- **EOF**：固定 7 个隐性位，格式错误会触发错误帧。

## 2. 标准帧与扩展帧

扩展帧（CAN 2.0B）把 ID 扩展到 29 位，结构上做了三处调整：

| 项目 | 标准帧 | 扩展帧 |
|---|---|---|
| ID 长度 | 11 位 | 11 位基本 ID + 18 位扩展 ID |
| IDE 位 | 显性 | 隐性（位于基本 ID 之后） |
| 额外字段 | 无 | SRR（替代远程请求位，固定隐性）、IDE、18 位扩展 ID |
| 仲裁场长度 | 12 位 | 32 位 |
| 适用场景 | 节点较少、ID 空间充足 | J1939、诊断、需要大量 ID 的系统 |

扩展帧的仲裁规则保证标准帧优先：扩展帧在 SRR 位置发送隐性位，而标准帧在同一位置的 RTR 位在数据帧中是显性，因此基本 ID 相同的标准帧会赢得仲裁。这个规则让混合网络中的标准帧不受扩展帧影响。

29 位 ID 不等于 29 位精度都用得上。J1939 把它分成优先级、PGN 和源地址三段使用，实际可用的 ID 空间与 11 位比是量级的提升，代价是每帧多出 20 个位的开销。

## 3. 远程帧

远程帧用于"请求某个 ID 的数据"，它的 RTR 位为隐性、没有数据场，DLC 表示请求的字节数。收到远程帧的节点如果负责该 ID，会以数据帧响应。

远程帧在现代系统中已经很少使用，原因是它有一个明显的缺陷：远程帧和数据帧共享同一个 ID，总线上无法区分"这是一次请求"和"这是一次响应"，多节点系统中容易出现应答冲突；而且用远程帧实现轮询时，请求和响应的延迟难以界定。现在更常见的做法是让主节点主动周期发送数据，或者用 UDS 等高层协议做显式的请求-响应。

## 4. 错误帧

错误帧由检测到错误的节点发出，作用是让总线上所有节点知道当前帧无效并丢弃它。错误帧由两部分组成：

- **错误标志**：主动错误节点发 6 个连续显性位（会破坏位填充规则，从而被其他节点识别为错误）；被动错误节点发 6 个连续隐性位。
- **错误定界符**：8 个隐性位。多个节点同时检测到错误时，各自的错误标志叠加，总线的显性区间可能比 6 位更长，但不会超过错误定界符的起点。

错误帧不携带任何数据或标识，只有"这一帧作废"这一个语义。区分主动与被动错误标志的意义在于：被动错误节点已经连续出错多次，让它保持隐性可以避免它继续干扰总线。

## 5. 过载帧

过载帧的结构与错误帧相同（6 个显性位 + 8 个隐性位），但含义不同：它表示接收方需要延迟下一帧。过载帧在两种情况下发出：接收方内部需要更长的处理时间，或者在间歇场（帧间隔的 3 个位）期间检测到显性位。

现代控制器的接收缓冲和中断响应通常足够快，过载帧在正常系统中很少出现。如果逻辑分析仪上频繁观察到过载帧，通常意味着接收端软件处理不过来（中断被长时间关闭、接收 FIFO 溢出），属于软件问题而不是总线问题。

## 6. 帧间隔与总线空闲

帧与帧之间有三种间隔：

- **间歇场**：3 个隐性位。这一段时间内所有节点都不允许开始发送，给其他节点处理接收的时间。
- **总线空闲**：任意长度的隐性位。总线在此状态下任何节点都可以开始发送。
- **暂停传输**：仅被动错误节点在发送完一帧后需要额外等待 8 个隐性位才能开始下一次发送，这是对被动错误节点的额外惩罚，让它在错误频发时进一步降低对总线的影响。

## 7. 帧位数与总线负载率

计算总线负载率的起点是帧的总位数。以标准数据帧、8 字节数据、无位填充为例：

| 部分 | 位数 |
|---|---|
| SOF | 1 |
| 仲裁场（11 位 ID + RTR） | 12 |
| 控制场（IDE + r0 + DLC） | 6 |
| 数据场 | 64 |
| CRC 场 | 16 |
| ACK 场 | 2 |
| EOF | 7 |
| 间歇场 | 3 |
| 合计 | 111 |

即每帧约 111 位。8 字节数据只占 64 位，固定开销约 47 位，有效载荷比例约 58%。

位填充会让实际位数增加，最坏情况下每 5 位插入 1 位，因此上表的数字要乘一个填充系数。实用的估算方法是对具体的 ID 和数据内容用工具或表格计算，或者按最坏情况（位数 × 1.2）保守估算。

**总线负载率** = 所有帧的位数 × 发送频率之和 ÷ 波特率。例如 20 个节点各以 10 ms 周期发送一帧 111 位的标准帧：

$$
\text{负载率} = \frac{20 \times 111 \times 100}{500000} \approx 44\%
$$

这个值已经在建议上限边缘，继续增加节点或提高频率会让低优先级帧的延迟明显变差。

## 8. 在逻辑分析仪上核对帧

用支持 CAN 解码的逻辑分析仪或 CAN 分析仪抓帧时，建议按以下顺序核对：

1. **位时序是否正确**：解码器需要正确的波特率，波特率错了会看到大量错误帧或完全解不出帧。
2. **ID 与数据是否符合协议表**：逐字段比对，特别注意字节序。
3. **DLC 与实际数据长度是否一致**：DLC 与数据场长度不符说明是手工构造的帧，需要检查发送代码。
4. **错误帧出现的位置和频率**：集中在某个时间点说明是外部干扰或某个节点异常；持续出现说明物理层有问题。
5. **帧间隔是否稳定**：周期帧的间隔抖动过大可能是软件发送逻辑基于任务调度而非定时器触发。

具体的物理层与调试手段见 [[05-Communication/03-CAN总线/004-物理层与拓扑设计|物理层与拓扑设计]] 和 [[05-Communication/03-CAN总线/007-嵌入式实现与调试|嵌入式实现与调试]]。
