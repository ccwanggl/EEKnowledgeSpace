# 嵌入式网络应用协议

应用层协议决定了设备与外界交换数据的方式，选择依据不是"哪个流行"，而是连接数、报文频率、可靠性责任归属和实现资源。本笔记按这一组判据梳理嵌入式常用的六类协议，并给出选型对照。

## 1. HTTP 服务端的两种形态

静态页面 + CGI/SSI 形态：把 HTML、CSS、JavaScript 放在只读文件系统或编译进固件的常量数组中，服务器只负责查找与发送；动态数据通过 CGI（表单提交触发处理函数）或 SSI（在页面中嵌入占位标记，发送时替换为实时值）注入。SSI 的服务器开销极小，适合状态展示；CGI 可处理配置写入但需要解析请求体。

REST 风格接口形态：用 JSON 或紧凑二进制承载数据，按资源路径与方法来映射处理函数。开销主要取决于响应体序列化方式——JSON 需要格式化和浮点转字符串，是大响应场景下的 CPU 热点，可考虑预分配固定缓冲直接拼接。

资源开销的关键点：并发连接数受 TCP 连接池限制，HTTP/1.1 的 Keep-Alive 会长期占用连接控制块，若客户端不断开而设备连接池有限，新客户端会被拒绝。响应缓冲建议放在应用静态数组中而非内存堆。大文件、图片和 TLS 对 MCU 资源消耗大，需要在设计阶段确认 Flash 与 RAM 余量。

## 2. MQTT 的发布订阅模型与 QoS 语义

MQTT 通过 Broker 解耦发布者与订阅者：设备以 Client ID 连接，发布到主题（Topic），订阅带通配符的主题过滤器（`+` 匹配单层，`#` 匹配多层）。主题按层级用 `/` 分隔，设计时应避免以 `#` 订阅全量，也应避免主题中含动态唯一值导致 Broker 端订阅表膨胀。

| QoS | 语义 | 报文交互 | 开销与用途 |
|---|---|---|---|
| 0 | 最多一次 | PUBLISH | 无确认，最小开销，丢包不补 |
| 1 | 至少一次 | PUBLISH → PUBACK | 可能重复，应用需幂等，最常用 |
| 2 | 恰好一次 | PUBLISH → PUBREC → PUBREL → PUBCOMP | 两轮往返，开销最大，仅用于不可重复的操作 |

QoS 只保证设备到 Broker 一段，端到端语义还要看 Broker 到订阅者的 QoS 与持久会话设置。QoS 2 在低带宽链路上会显著放大延迟，多数遥测场景用 QoS 1 加幂等处理即可。

控制报文固定头为 1 字节类型与标志加 1~4 字节剩余长度，因此最小报文为 2 字节；PINGREQ/PINGRESP 各只有 2 字节，是最经济的保活报文。Keep Alive 是客户端在 CONNECT 中声明的最大空闲间隔，服务端在 1.5 倍该时间内未收到任何报文就判定客户端离线。遗嘱消息（Will）在 CONNECT 时声明，客户端异常断开时由 Broker 代为发布，用于让其他设备获知掉线；正常断开（发送 DISCONNECT）不会触发遗嘱。

库的选择：Eclipse Paho（Arduino/STM32 等平台有移植）、ESP-MQTT（ESP-IDF 内置）。实现时需要提供的底层能力是 TCP 连接建立、定时器（保活）与可选的 TLS 通道。

## 3. CoAP 与 MQTT 的取舍

CoAP 是运行在 UDP 上的 REST 风格协议，用方法码（GET/POST/PUT/DELETE）和 URI 路径操作资源，报文头固定 4 字节加选项与负载。相比 MQTT 的特点：

- 无连接，不需要长连接的保活开销，适合需要长时间休眠的设备；
- 支持观察模式（Observe），客户端注册后由服务端在资源变化时推送，语义接近 MQTT 订阅；
- 可靠性可选：CON 类型报文需要 ACK，NON 类型不需要；重传由客户端按超时倍增执行；
- 安全由 DTLS 提供，与 TCP 上的 TLS 是不同实现路径，握手报文更小但实现同样占资源。

选择判据：需要长连接、双向命令、成熟云平台接入选 MQTT；需要极低功耗、报文稀疏、已有 CoAP 服务端（如部分 LwM2M 平台）选 CoAP。两者都能通过网关互转，网关会增加一跳延迟和部署复杂度。

## 4. Modbus TCP 与 Modbus RTU 的差异

Modbus TCP 沿用 Modbus 的功能码与数据模型（线圈、离散输入、保持寄存器、输入寄存器），但在 TCP 之上增加了 MBAP 头：2 字节事务标识、2 字节协议标识（固定 0）、2 字节长度、1 字节单元标识，之后才是功能码与数据。标准端口为 502。

与 Modbus RTU 的关键差异：

| 维度 | Modbus RTU | Modbus TCP |
|---|---|---|
| 承载 | 串行（RS-485/RS-232） | TCP |
| 校验 | CRC-16 | 由以太网 FCS 与 TCP 校验保证 |
| 寻址 | 从站地址 1~247 | 单元标识（常用于网关后的从站地址） |
| 定界 | 帧间静默间隔 | MBAP 长度字段 |
| 事务匹配 | 依赖请求响应顺序 | 事务标识可支持流水线 |

网关实现（Modbus TCP ↔ RTU）需要处理三件事：事务标识与串行请求的映射、串行总线的独占访问（同一时刻只能有一个 RTU 事务在途）、以及超时与异常码回传（把 RTU 超时转换为 TCP 侧的错误响应而不是静默丢弃）。并发 TCP 客户端向同一串口发起请求时必须排队，否则响应会串线。

库的选择：libmodbus、FreeModbus。实现时注意保持寄存器的地址偏移约定（协议地址与文档地址常相差 1）与字节序约定（同一寄存器内的高低字节顺序在设备间不一致，需以对端文档为准）。

## 5. TFTP、SNMP 与其他轻量协议

- TFTP：UDP 上的简单文件传输，端口 69，块大小默认 512 字节，支持读写与选项协商（块大小、超时、传输大小）。协议极简适合固件升级引导，但没有认证与完整性校验，升级流程必须自带镜像校验；丢包环境下小块大小会显著降低效率。
- SNMP：用于设备监控，报文以 ASN.1 BER 编码，代理需要维护 MIB 对象。嵌入式常用 SNMPv2c（团体名明文）或 SNMPv3（带认证与加密），实现资源开销随 MIB 规模增长。
- FTP：双连接（控制 + 数据），实现复杂、明文传输，在嵌入式上一般被 TFTP 或 HTTP 替代；原文所列 FTP 属于应用层可选协议，是否实现取决于对端要求。

## 6. NTP 时间同步

NTP 客户端向服务器 123 端口发送 48 字节请求，收到含时间戳的响应后按往返时延的一半修正本地时钟。常见做法是周期同步（数分钟到数小时）而不是持续校准。

对有 TLS 校验、日志时间戳、证书有效期判断的设备，时钟必须在上电后尽快同步，否则会出现证书校验失败或日志时间错乱。设备无网络时应有备用时间源（RTC 或手工设置），并明确未同步状态下的降级行为。NTP 不提供认证时易受伪造响应影响，安全要求高的场景应使用带认证的 NTP 或 PTP。

## 7. 协议选型对照

| 协议 | 承载 | 默认端口 | 可靠性责任 | 典型资源特征 | 适用场景 |
|---|---|---|---|---|---|
| HTTP | TCP | 80（TLS 443） | TCP | 连接与响应缓冲较大 | 配置页面、REST 接口 |
| MQTT | TCP | 1883（TLS 8883） | 按 QoS | 长连接 + 保活定时器 | 云平台遥测与命令 |
| CoAP | UDP | 5683（DTLS 5684） | 应用可选 | 无连接，报文小 | 低功耗、稀疏上报 |
| Modbus TCP | TCP | 502 | TCP | 多连接 + 寄存器映射 | 工业 PLC/HMI |
| TFTP | UDP | 69 | 应用自行重传 | 块缓冲 | 固件升级 |
| SNMP | UDP | 161/162 | UDP | MIB 编解码 | 网络管理 |
| NTP | UDP | 123 | UDP | 48 字节报文 | 时间同步 |

选型时先确定三件事：是否需要长连接与服务器主动下发、是否允许丢包由应用补偿、设备是否需要休眠。这三项决定后，剩下的差异主要是报文格式与生态支持。TLS 与 DTLS 的额外成本见 [[05-Communication/06-以太网与TCP-IP/006-网络安全与TLS|网络安全与 TLS]]；socket 层的收发与并发写法见 [[05-Communication/06-以太网与TCP-IP/004-Socket编程与并发模型|Socket 编程与并发模型]]。
