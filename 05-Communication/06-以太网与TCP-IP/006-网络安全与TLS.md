# 网络安全与 TLS

在嵌入式设备上启用 TLS 不是"打开一个开关"，而是要在算力、RAM、Flash、密钥存储和证书生命周期管理之间做出明确取舍。更常见的问题是：TLS 已经启用，但证书校验被关闭或写得无效，通信仍然可被中间人解密——这种配置的安全性与明文相当。

## 1. 加密通道的实际代价

握手阶段的开销远高于数据传输阶段：

- 计算量：ECDHE 密钥交换与 ECDSA/RSA 签名验证是握手的主要算力消耗，RSA-2048 验签与 ECDHE P-256 的耗时在无硬件加速的 Cortex-M4 级别 MCU 上通常在数十到数百毫秒量级；采用 RSA-2048 私钥操作（如作为服务端或做客户端证书认证）会明显更慢。实际数值随主频、编译器优化与所用算法库差异很大，应以目标平台实测为准。
- RAM：每个 TLS 连接需要握手缓冲、会话密钥、哈希与密码上下文。典型 mbedTLS 配置下单连接的静态与动态占用在数十 KB 量级，且与服务端证书链长度、最大记录长度、是否启用会话复用相关。RAM 峰值出现在握手阶段，配置不足的直接表现是握手过程中返回内存错误。
- Flash：密码套件、哈希算法与证书解析代码本身占数十到上百 KB，裁剪掉不用的套件是首要手段。
- 时间：握手往返次数增加连接建立延迟；长连接复用（session resumption）可以摊薄这一成本，但需要保存会话票据并处理其有效期。

## 2. 算法库与硬件加速的选择

| 方案 | 特点 | 适用条件 |
|---|---|---|
| mbedTLS | 与 lwIP 同源生态，模块化配置，文档与移植资料多 | 通用 MCU，需按需裁剪配置头 |
| wolfSSL | 体积与性能经过优化，商业支持与认证较完整 | 对体积或合规有要求 |
| 硬件加密引擎 | AES/SHA/PKA 卸载，降低 CPU 占用与握手时间 | MCU 带 CRYPTO/HASH/PKA 外设，需驱动与库适配 |

硬件加速并非全自动：需要确认库是否已适配该外设、哪些操作被卸载（通常是对称加密与哈希，非对称可能仍需软件实现或部分加速）、以及 DMA 与缓存一致性带来的额外处理。启用前后应对比握手时间，而不是假定一定更快。

## 3. 证书校验为什么必须做

TLS 提供的是机密性、完整性与身份认证三件事，只做加密不校验证书就丢掉了身份认证，攻击者可以用自签证书冒充服务器完成握手。常见错误做法：

- 把校验回调写成无条件返回成功（`verify` 恒为 0 或跳过 `mbedtls_ssl_conf_verify`）；
- 只校验有效期而不校验签发链与主机名；
- 把 CA 证书换成服务器自签证书后仍保留"校验通过"，等于固定信任任意证书；
- 信任链只加载根 CA，但服务端发送的链不完整，客户端因找不到签发者而失败——这类失败应通过补全服务端链解决，而不是关闭校验。

正确做法是加载预期的根 CA（或中间 CA）到信任存储，启用主机名校验，并在校验失败时让连接失败而不是降级继续。自签名部署场景可以固定信任该特定证书（证书固定，certificate pinning），但必须理解这意味着更换证书需要同步更新设备。

## 4. 证书与密钥的存储

密钥泄露等同于身份被冒用。存储方案按防护强度递增：

- 内部 Flash 分区：成本最低，可读性取决于是否启用读保护和调试口禁用；量产时应关闭调试接口或设置读保护等级，具体选项以所用 MCU 的选项字节/熔丝说明为准。
- 外部 Flash：便于容量扩展与现场更新，但通常可被直接读取，必须配合加密存储或至少确认物理访问边界可信。
- 安全元件 / 安全芯片：私钥不出芯片，签名与密钥协商在芯片内完成，提供防篡改与抗侧信道能力；代价是成本、接口驱动与吞吐限制。
- 一次性烧录（OTP）/ 熔丝：适合写入不可变的设备身份密钥，不可更新，需在量产流程中严格管控。

工程上还需要解决三个流程问题：唯一设备证书的签发与注入、证书到期前的更新机制、以及证书被吊销后的处理（嵌入式端一般无法实时查询吊销列表，常以短有效期加自动续签替代）。

## 5. 对称密钥与预共享密钥方案

设备算力极度受限、或与自有服务端通信时，可采用预共享密钥（PSK）方案：TLS-PSK 密码套件用对称密钥完成认证与密钥派生，避免非对称运算，握手时间与代码体积都显著小于证书方案。

- 优点是省算力、省 Flash、不需要证书链解析；
- 缺点是密钥分发与轮换困难，无法区分设备身份（除非一机一密），且部分云平台不支持 PSK 套件；
- 一机一密是必要的：全设备共用同一 PSK 时，单台设备被拆解即导致全部设备可被冒充。

除 TLS 之外，应用层自建对称加密（如对报文做 AES-GCM 并带序号防重放）也能在受控范围内提供机密性与完整性，但认证机制需要自行设计，出错概率高于使用成熟 TLS 实现。

## 6. 安全启动与固件签名升级

TLS 保护的是传输过程，不能防止设备运行被篡改的固件。完整链条是：安全启动验证启动镜像的签名（信任根固化在不可改写的区域），安全升级在写入前验证下载镜像的签名，二者共用同一套密钥与算法。

实现要点：签名验证必须在写入 Flash 之前完成（或写入后、跳转前完成，但此时需保留回滚能力）；升级镜像需要包含版本号以防降级攻击；双分区（A/B）方案可在验证失败时回退到旧镜像。签名私钥的保管等级应高于设备密钥，通常在离线环境或 HSM 中完成签名。

## 7. 端口暴露与攻击面收敛

- 关闭不需要的服务：未使用的协议栈功能、调试服务（Telnet、未保护的 HTTP 管理页）、示例程序中的回显服务；
- 管理接口优先只监听内网地址或指定网口，而不是 `INADDR_ANY`；
- 对连接数与半开连接做限制，防止资源耗尽；
- 认证失败要有速率限制或延迟，避免被暴力猜测；
- 更新失败、异常复位时的行为要明确（例如复位后是否保留升级标志位），避免出现可被触发的降级路径。

攻击面的收敛应与 lwIP 裁剪一致：关闭 `LWIP_*` 中不用的协议不仅省 RAM，也直接减少可被利用的解析代码。

## 8. 常见问题

| 现象 | 常见原因 |
|---|---|
| 证书校验始终失败并提示时间错误 | 设备时钟未同步到可信时间源，导致有效期判断失败；应在联网后先完成 NTP 同步再建立 TLS |
| 握手过程中返回内存不足 | 握手缓冲与会话上下文超出配置的堆大小；检查最大记录长度、证书链长度与会话数上限 |
| 与部分服务器握手成功、部分失败 | 密码套件或 TLS 版本不被对端接受；分组密码套件与椭圆曲线配置未包含对端要求的组合 |
| 随机数质量不足导致密钥强度下降 | 使用固定种子或软件伪随机源；应使用硬件随机数发生器或在启动时采集足够的熵，具体熵源以所用 MCU 与库说明为准 |
| 长时间运行后连接建立失败 | 会话对象未释放或证书解析缓冲泄漏，需检查关闭路径与错误分支 |

随机数生成器是 TLS 的安全根基。没有硬件 TRNG 的平台必须在启动阶段收集熵，且不能把固定常量当作种子。这一项无法通过功能测试发现，只能通过代码审查确认。
