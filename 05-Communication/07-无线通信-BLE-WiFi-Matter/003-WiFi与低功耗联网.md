# WiFi 与低功耗联网

WiFi 是唯一同时具备"路由器直连、无需网关、天然 IP 可达"三项特性的无线技术，因此智能家居和视频类产品几乎默认选它。代价也很明确：802.11 的载波侦听与确认机制让无线电必须长时间开机，即使只发几十字节数据，配合路由器的 DTIM 节奏也会带来毫安级的平均电流。判断一个产品该不该用 WiFi，本质上是在问"它有没有条件持续接入市电或频繁充电"。

## 1. 802.11 各代与频段、信道宽度、MIMO 的对应

| 标准 | 商用名称 | 频段 | 信道宽度 | MIMO 与调制要点 |
|---|---|---|---|---|
| 802.11b | — | 2.4GHz | 20MHz | DSSS/CCK，1~11Mbps，抗干扰能力弱 |
| 802.11a/g | — | 5GHz / 2.4GHz | 20MHz | OFDM，最高 54Mbps，g 在 2.4GHz 与 b 后向兼容 |
| 802.11n | WiFi 4 | 2.4/5GHz | 20/40MHz | 引入 MIMO 与帧聚合，理论速率取决于空间流数 |
| 802.11ac | WiFi 5 | 5GHz | 20/40/80/160MHz | 更多空间流、更高阶调制，仅 5GHz |
| 802.11ax | WiFi 6 | 2.4/5GHz（6E 增加 6GHz） | 20~160MHz | OFDMA、上行 MU-MIMO、目标唤醒时间 |

原笔记中"11n 150Mbps、11ac 1Gbps、11ax 2.4Gbps"是特定配置下的标称速率，不是单空间流或单天线的通用值：150Mbps 对应 802.11n 的 20MHz、单空间流、短保护间隔组合，1Gbps 与 2.4Gbps 则需要多空间流和更宽信道。选型时应把标称速率当作上限看，实际可用吞吐由空间流数、信道宽度、保护间隔和协议开销共同决定。

## 2. 标称速率与实测吞吐的差距来源

差距来自协议开销与环境。每个数据帧前有前导与报头，收到正确帧后需要回 ACK，帧间还要留固定的间隔时间；小包场景下这些开销占比极高，发送 100 字节数据的效率远低于发送 1500 字节。20MHz 信道在 2.4GHz 只能容纳 3 个互不重叠的信道（常见为 1、6、11），邻居路由器一多，同一信道上的设备要按 CSMA/CA 排队，吞吐随节点数下降。此外重传、速率自适应降级（信道变差时自动降调制档位）和加密开销都会吃掉带宽。

工程上的经验做法是把"应用层需要多少带宽"乘以 2~3 倍作为对 WiFi 链路的真实要求，并优先实测：用 iperf 类工具在同信道干扰下测吞吐，比看数据手册的标称速率更有意义。

## 3. 功耗特性与省电模式

WiFi 设备即使在空闲时也需要周期性醒来监听信标（Beacon），因为路由器可能在任意时刻缓存下行数据。省电模式的核心是把这段监听占空比压到最低：

**Modem sleep** 让射频在两次 DTIM 之间关闭，只在信标指示有缓存数据时才醒来接收。DTIM 周期由路由器配置，常见值为 1~3 个信标间隔（信标间隔典型 100ms），因此监听间隔通常在 100~300ms 量级；DTIM 越大越省电，下行数据到达延迟越大。

**Light sleep** 进一步关闭部分时钟域，只保留必要的唤醒源。它需要 MCU 与射频协同，唤醒后要重新与路由器同步，因此会受到路由器的信标节奏限制而非完全自主。

**Deep sleep** 则等于断开 WiFi，唤醒后要重新扫描、关联、认证并获取 IP，整个流程通常需要数百毫秒到数秒，期间电流维持在数十至上百毫安。这就是"为什么 WiFi 不适合高频电池设备"：即使数据量极小，保持连接本身就要求周期性射频活动，而重新连接的代价又高到无法频繁执行。相比之下 BLE 广播一个 31 字节包只需要几百微秒的射频时间。

## 4. 配网方式的用户与可靠性权衡

设备出厂时没有 WiFi 凭证，把它安全地送进设备是产品体验的第一个坎。

**SmartConfig 类方式**（含各类"一键配网"）通过手机 App 把 SSID 与密码编码进特殊的广播帧，设备在混杂模式下抓包解析。优点是不需要切换手机网络，缺点是依赖手机与路由器的具体实现、在部分机型或 5GHz 环境下成功率明显下降，且凭证以明文方式在空中传输，安全性依赖上层加密。

**AP 配网**让设备自己开一个热点，手机连上后通过网页或 App 填入凭证。可靠性最高、实现最直观，代价是用户需要手动切换 WiFi 并可能遇到"连上热点后无法上网"的系统提示。

**蓝牙配网**用 BLE 承载凭证交换，可以做到加密与双向认证，用户体验好（无需切网），代价是设备需要同时具备 BLE 与 WiFi 射频，且配网期间两条链路要协同。

**二维码配网**把凭证通过摄像头读入，适合带屏幕或摄像头的设备，读取失败率低但要求用户操作准确。

选择时要考虑的是失败后的恢复路径：任何配网方式都可能失败，产品必须能在失败后重新进入配网模式，而不是变成一块砖。

## 5. TCP/IP 与 TLS 在 MCU 上的开销

MCU 上跑的通常是 lwIP 之类的精简协议栈，TCP 需要维护发送/接收窗口、重传队列和定时器，每条连接都占用固定内存；同时开多条连接时 RAM 很快见底。TLS 的开销更值得提前核算：握手需要非对称运算与证书验证，服务端证书链越长、验证越严格，握手耗时和峰值内存越高；会话恢复机制可以减少重复握手，但需要保存会话状态。

实际设计要点是：把 TLS 的峰值内存按"握手阶段"而非"数据阶段"估算，为收发缓冲区、证书解析和随机数预留余量；对频繁短连接的应用优先复用长连接或使用会话恢复；若设备只需要上报数据，考虑用轻量协议替代完整的 HTTP 请求-响应模型。协议栈裁剪与 TLS 实现细节见 [[05-Communication/06-以太网与TCP-IP/002-TCP-IP协议栈与嵌入式裁剪|TCP/IP 协议栈与嵌入式裁剪]] 与 [[05-Communication/06-以太网与TCP-IP/006-网络安全与TLS|网络安全与 TLS]]。

## 6. OTA 升级与断点续传

WiFi 的带宽让 OTA 变得可行，但也带来风险：升级包通常比应用本体大，下载过程中断电或断网会让设备处于"半新半旧"状态。可靠做法是双分区方案——新固件写入备用分区，校验通过后再切换启动分区，失败则回退到旧分区。断点续传需要服务端支持按 Range 请求获取指定字节区间，设备把已下载长度持久化，重启后从断点继续，同时用分块校验（如每块 CRC）确认已写入部分的完整性。

常见的失败模式包括：写入 Flash 时被看门狗复位、下载与业务逻辑争抢内存导致 OOM、切换分区后新固件的 BLE/WiFi 校准数据与旧分区不匹配。设计时要把"升级中"当作独立状态机，明确每个阶段掉电后的恢复动作。

## 7. 方案选型

ESP32 系列是嵌入式 WiFi 的主流选择：单芯片集成 WiFi 与 BLE，官方 SDK 与示例完备，成本低；不同型号在射频能力、是否支持 WiFi 6、是否集成 802.15.4 上有差异，选型应以产品线文档为准，见 [[04-Microcontrollers/03-ESP32系列/001-产品线|ESP32 产品线]]。ESP32-C6 同时具备 WiFi 6、BLE 5 与 802.15.4，适合既要 WiFi 又要 Thread/Matter 的产品。

Realtek RTL8720/RTL8722 面向低成本 WiFi MCU 场景；WizFi360 一类模块提供 AT 指令接口，把网络协议栈放在模块内部，适合主控资源紧张或希望与既有 MCU 解耦的场合；ESP-AT 同样让你用 UART 驱动 ESP32 的联网能力，代价是主控与模块之间的串口成为吞吐与延迟瓶颈。选型时需要核对的不只是价格：AT 固件是否支持 TLS、同时连接数、是否支持透传模式、OTA 由谁负责、模块认证是否覆盖目标市场。

## 8. 常见问题与排查方向

**信道拥塞**：表现为延迟抖动大、吞吐不达预期。用信道扫描确认邻居分布，把设备固定到相对空闲的信道，或改用 5GHz（代价是穿墙能力下降）。

**DTIM 与延迟冲突**：应用要求秒级下行响应，但省电模式把监听间隔拉长到数百毫秒。解决方向是降低 DTIM 周期（牺牲功耗）或改用长连接保活机制，同时检查是否被路由器强制覆盖了省电策略。

**路由器兼容性**：部分路由器对省电客户端、WPA3 过渡模式或 802.11 的某些可选特性实现不一致，导致反复掉线。排查时用一台已知可用的路由器做对照，并记录设备与路由器两端的日志时间戳。

**天线布局差导致断连**：模块贴近金属外壳、电池或大块铺铜时，辐射效率显著下降，表现为同距离 RSSI 明显偏低。这类问题在现场很难通过软件解决，需要回到布局与净空设计，参见 [[06-PCB-Design/00-README|PCB 设计]]。

**掉线重连机制**：必须明确区分"短时丢包"与"真的断连"，为断连设计指数退避的重连策略并设置上限，避免设备在无路由器环境中持续以最大功率扫描导致电池被迅速耗尽；同时避免重连流程与业务唤醒互相抢占，造成状态机死锁。
