# Thread、Zigbee 与 Matter

这三者经常被并列提起，但它们不在同一层：Zigbee 和 Thread 是两套建立在 IEEE 802.15.4 物理层之上的完整协议栈，Matter 则是运行在 IP 之上的应用层标准，可以承载在 Thread、WiFi 或以太网之上。把它们混为一谈会导致选型时反复摇摆——真正需要先决定的是"用哪张网状网络"，再决定"在网络之上放哪套应用层"。

## 1. IEEE 802.15.4 物理层与 MAC 基础

802.15.4 在 2.4GHz 频段定义了 16 个信道，信道间隔 5MHz，采用 OQPSK 调制配合 DSSS，空中速率 250kbps。它在 2.4GHz 上另有多个区域性频段，可用的信道编号与频率随地区不同，选型时要确认目标市场对应的子频段。

MAC 层使用带冲突避免的载波侦听多址（CSMA/CA），并在需要确定性时隙的应用中使用超帧结构：协调器周期性发送信标，划分出竞争访问期与保证时隙。绝大多数消费类产品只使用非信标模式，也就是节点在发送前随机退避、侦听后发送，收到 ACK 才算成功。802.15.4 的 MAC 帧支持确认与重传，但重传次数和退避策略由上层协议栈决定，因此"同一物理层"不等于"同一可靠性表现"。

## 2. Zigbee 的网络角色与路由

Zigbee 定义了三种节点角色：协调器（Coordinator）负责建网、分配地址和维护网络参数；路由器（Router）是市电供电、参与转发的中继；终端设备（End Device）通常电池供电，可以周期性休眠，其下行消息由父节点缓存后再取回。终端设备不参与转发，这是它能省电的前提，也意味着"网状覆盖"实际上由路由器和协调器的布点质量决定。

Zigbee 使用按需距离矢量（AODV）类路由，节点按需发起路由发现并维护路由表；链路失效时触发路由修复。它的应用层由 Zigbee Cluster Library（ZCL）定义：属性（Attribute）、命令（Command）和报告机制构成标准化的设备行为，例如开关、调光、温度测量各自对应一组簇。Zigbee 3.0 统一了此前分散的应用规范并引入 Green Power 等能力，存量生态包括 Philips Hue、IKEA 和小米等大量设备，这是它至今仍被大量部署的主要原因。

## 3. Thread 的 6LoWPAN 与 IPv6 承载

Thread 同样跑在 802.15.4 上，但它把 IPv6 带进了低功耗网状网络，关键在于 6LoWPAN 头压缩：把 40 字节的标准 IPv6 报头压缩到几个字节，否则在最大 127 字节的 802.15.4 帧里几乎无法承载应用数据。压缩依赖上下文的建立与维护，链路建立阶段通过 Mesh Link Establishment 完成设备能力发现、链路参数配置和路由信息交换。

Thread 网络中的节点角色可以动态变化：Router 承担转发与路由维护，可升级为 Leader 负责分配路由器地址和聚合网络数据；Router-eligible End Device 具备成为路由器的能力但暂不承担转发；Sleepy End Device 长时间休眠，通过父节点取回下行数据；Border Router 提供到其他 IP 网络的通路，它同时是 Thread 网络与家庭局域网之间的路由器与边界。网络自愈表现为链路失效后重新选路、路由器数量不足时提升候选节点，路由器数量本身受设计约束（数量过多会加重路由开销），因此布点不是越多越好。

Zigbee 的地址分配与功耗模型值得单独说明。协调器在建网时确定网络参数，路由器与终端从父节点获得网络地址；终端设备可以设置较长的轮询间隔，父节点在这段时间里为它缓存下行帧，缓存深度有限，超出后新帧会被丢弃——这就是"设备偶尔收不到控制命令"的常见原因，解决方向是缩短轮询间隔或让父节点及时上报缓存溢出。Zigbee 网络规模受地址空间与路由表内存限制，实际部署中几十到几百节点是常见区间，超过之后建网时间、路由表开销与广播风暴都会明显恶化。

Thread 的网络规模同样受路由器数量与内存约束，设计目标是家庭与小规模商用场景。它的地址体系基于 IPv6，终端可以拥有多个地址（链路本地、网格本地、全局），应用层看到的始终是 IP 地址，因此不需要像 Zigbee 那样处理短地址与端点映射。

## 4. 同物理层的共存与信道规划

Zigbee 与 Thread 使用同一物理层，但帧格式、地址体系和路由机制完全不同，两者不能互通，也不共享信道协调机制。当它们与 WiFi 共处一室时，三者会争抢 2.4GHz 频谱：WiFi 的一个 20MHz 信道覆盖约 10 个 BLE 信道或 4 个 802.15.4 信道。

因此信道规划要在项目一开始就定：确认现场 WiFi 占用了哪些信道，然后把 Zigbee/Thread 网络固定在远离这些频段的位置，并保证同一空间内的多个 802.15.4 网络使用不同信道。Zigbee 的协调器和 Thread 的 Leader 都允许在建网时做能量扫描以选择较干净的信道，但一旦建网完成，改信道意味着整个网络重建（部分实现支持信道迁移，但设备侧行为需要逐一验证）。

## 5. Matter 的定位与传输承载

Matter 由 Connectivity Standards Alliance 制定，目标是把智能家居的应用层语义标准化，让同一设备能被不同生态的控制器识别和操作。它不定义新的物理层：运行在 WiFi、以太网或 Thread 之上，在 Thread 场景中依赖边界路由器把 IPv6 流量带出网状网络。

Matter 采用统一的数据模型，把设备描述为端点（Endpoint）、簇（Cluster）和属性/命令，并规定设备类型及其必需簇。安全方面要求设备具备设备认证证书，配网时校验设备身份，运行阶段使用加密会话，控制指令优先在本地局域网内完成而不依赖云端，这也是"本地优先"的来源。

支持的设备类型覆盖灯、开关、插座、传感器、门锁、窗帘、温控器等常见品类，新增类型随规范版本推进，选型时应以目标规范版本的支持列表为准。

数据模型之外，Matter 还规定了属性的订阅与上报机制：控制器可以订阅某个属性并在数值变化超过设定阈值时收到上报，而不是持续轮询。这让低功耗设备可以只在必要时唤醒发送，但阈值设置过小会导致上报过于频繁，反而抬高功耗，因此订阅参数属于需要在产品侧验证的配置项。跨生态互操作还依赖设备类型的"必需簇"完整实现，缺失必需簇的设备即便能配网，也会在部分控制器的功能页面上表现为不可用。

## 6. 配网流程与凭证

Matter 的首次入网（Commissioning）通常分为两步：先用 BLE 建立临时通道传输配网信息与凭证，再由控制器把设备引入目标 IP 网络（Thread 凭证或 WiFi 凭证），完成后设备获得操作凭证并加入 fabric。设备侧常见的入口是二维码或配对码，两者都编码了设备标识与配网密码，因此包装与标签的保密性属于安全设计的一部分。

凭证模型决定了互操作边界：设备可以被加入多个 fabric（多个生态各自管理），但一旦某个 fabric 的控制器不可用，只有属于该 fabric 的控制关系失效，不影响其他生态。控制器形态包括手机 App、独立中枢设备和带 Matter 支持的语音助手，云端能力（远程访问、场景联动）取决于控制器是否提供。

Matter 认证是产品上市的前置条件：设备需要通过认证测试并获得证书，证书体系与设备认证证书绑定，未认证设备通常无法被主流控制器接受为正式设备。设备认证证书由芯片或模组厂商在产线注入，量产环节必须保证每个设备的证书与其唯一标识一致，否则会出现"样机能配网、量产机配不上"的问题。

## 7. Matter over Thread 的现实约束

选择 Thread 承载意味着产品必须假定现场存在边界路由器。边界路由器通常由智能音箱、电视盒子或专用网关承担，它需要常供电并具备良好的射频环境；边界路由器缺失、离线或距离过远时，Matter 设备会表现为"配网失败"或"配网成功但无法控制"。

因此 Matter over Thread 产品的说明文档需要明确写出边界路由器要求，固件也要处理边界路由器切换时的重新寻址与会话恢复。相比之下，Matter over WiFi 不依赖边界路由器，但设备本身要承担 WiFi 的功耗，适合市电供电设备。

边界路由器与 Thread 网络之间还有一层值得注意的分工：边界路由器对外提供 IPv6 前缀并做路由通告，对内向 Thread 网络提供通往家庭局域网的路径；它通常还承担服务注册和 mDNS 发现，使控制器能在局域网内找到设备。这意味着边界路由器的固件版本、支持的前缀委派方式和 mDNS 实现都会影响配网体验，排查"配网成功但控制器找不到设备"时要检查这一层而不只是射频信号。

另一个现实约束是设备侧的内存开销。Thread 的 IPv6 寻址、6LoWPAN 压缩上下文、Matter 的会话与订阅表都会占用 RAM，同时运行 Thread 与 BLE（配网期间两者并存）时峰值内存往往出现在配网阶段而不是稳态阶段；选型时按配网阶段的峰值而非稳态值评估余量，才能避免"平时跑得好、一配网就复位"。若产品同时需要 Zigbee 与 Thread，需要注意二者虽然物理层相同，但通常不能在同一射频上同时运行，切换协议意味着重启网络栈。

## 8. 芯片平台与选型

Thread 与 Zigbee 的共同要求是支持 IEEE 802.15.4 射频，Matter 则在此之上要求足够的 Flash/RAM 承载 SDK 与证书存储。ESP32-H2 面向 Thread/Zigbee 与 BLE 组合，ESP32-C6 在 WiFi 6 基础上增加了 802.15.4 与 BLE，适合需要同时做边界路由器或双协议的产品；nRF52840 是 Thread/Zigbee/BLE 的成熟单芯片方案，nRF5340 面向更高性能的双核场景；Silicon Labs 的 EFR32 系列与 TI 的 CC2652 在多协议并发和生态工具上各有侧重。

选型时要核对：是否支持所需的并发协议组合、是否有可用的 Matter SDK 支持（如 ESP-Matter 或芯片厂商的 Matter 例程）、Flash/RAM 余量、是否支持安全存储用于凭证与密钥。若产品要充当 Matter 控制器或边界路由器，还需要 Linux 级别的网络能力，见 [[10-RTOS与系统/05-嵌入式Linux入门/05-嵌入式Linux入门|嵌入式 Linux 入门]]；Zephyr 对 Thread 与 Matter 的原生支持可作为多协议固件的工程基础，见 [[10-RTOS与系统/03-Zephyr/03-Zephyr|Zephyr]]。具体的入网失败与信道问题排查见 [[05-Communication/07-无线通信-BLE-WiFi-Matter/007-无线协议选型与调试|无线协议选型与调试]]。

模块化选择也值得考虑：使用带认证的 Thread/Matter 模组可以把射频设计与认证压力转移给模组厂商，主控只需处理应用逻辑，代价是模组的供货与固件升级路线受制于供应商；单芯片方案（把射频与主控集成）成本更低、体积更小，但需要自己承担射频布局与认证。两者的取舍标准是产量、团队射频能力和认证时间预算，而不是单纯的 BOM 成本。
