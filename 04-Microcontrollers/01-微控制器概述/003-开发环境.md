# 开发环境

开发环境不只是编辑器。一个可以交付的 MCU 工程至少要把编译器、构建配置、芯片支持包、下载调试器、串口终端和版本化配置连成闭环。IDE 可以替换，芯片型号、编译参数、链接脚本和烧录方式必须能被其他人复现。

## 选什么环境

| 环境 | 适合的平台 | 适合的工作方式 |
|---|---|---|
| Arduino IDE | Arduino、部分 ESP32 和 RP2040 板卡 | 快速验证传感器、执行器和基础库 |
| STM32CubeIDE | STM32 | 从 CubeMX 配置到 HAL/LL、ST-LINK 调试的一体化流程 |
| CLion | STM32、ESP32、RP2040、Zephyr 与其他支持 GCC/IAR 的目标 | CMake 为主、跨平台、需要代码导航与重构的 C/C++ 工程 |
| VS Code + PlatformIO | 多平台，包括 STM32、ESP32、Arduino、RP2040 | 统一管理多块板、依赖、构建环境与命令行构建 |
| ESP-IDF | ESP32 系列 | Espressif 官方框架、Wi-Fi/BLE、FreeRTOS 与量产能力 |
| Keil MDK | Arm Cortex-M | 维护既有工程、使用专业调试与分析功能，或满足团队既定工具链要求 |
| Pico SDK | RP2040/RP2350 | Raspberry Pi Pico 的 C/C++ 与 CMake 原生开发 |

开发板、固件包、IDE 和调试器的版本会影响工程。不要只记录“使用了某 IDE”，还要记录完整料号、板卡版本、编译器版本、SDK/Pack 版本、下载器固件和构建配置。

## 所有环境都要先配置的内容

无论使用哪个 IDE，先完成以下检查，再写业务代码：

1. 安装与目标架构匹配的交叉编译器，例如 Arm 的 `arm-none-eabi-gcc`、Espressif 工具链或 Pico SDK 所用 GCC；
2. 选择准确的芯片、封装或开发板定义，确认时钟、Flash、RAM 和上传接口没有被默认值替代；
3. 建立下载与调试连接，确认 SWD/JTAG、USB 或串口端口，先读出芯片 ID 或烧录一个最小程序；
4. 将编译器、链接脚本、优化级别、宏、SDK/Pack 版本和下载配置写入项目文件，不依赖个人全局设置；
5. 保留 ELF、映射文件和串口波特率等诊断信息，发布构建与调试构建分开。

## STM32CubeIDE：适合从硬件配置开始

1. 在 CubeMX 或 CubeIDE 中选择准确料号和板卡，配置引脚、时钟树、外设、DMA 与 NVIC；
2. 生成工程后，先确认 `Debug` 构建可输出 ELF 和映射文件，再连接 ST-LINK 下载；
3. 在调试配置中核对调试接口、复位方式和 SWD 频率。首次上板或连接不稳时使用较低 SWD 频率，并保留 NRST；
4. 将 `.ioc`、链接脚本、启动文件和项目设置提交到仓库。手写代码放在独立模块或 `USER CODE` 区域，重新生成后审查差异；
5. 用 MCO、GPIO 翻转或串口输出验证时钟和下载链路，再加入 DMA、RTOS 和功率输出。

STM32 的工具职责、固件包和生成代码边界见 [[04-Microcontrollers/02-STM32系列/003-Cube工具链、软件包与工程结构|Cube 工具链、软件包与工程结构]]。

## CLion：CMake 项目与嵌入式调试

CLion 适合把 STM32、ESP32、RP2040 等工程统一到 CMake 或既有 Makefile。它不会替代芯片 SDK、启动文件或下载器，重点是管理工具链、构建配置和调试会话。

### 最小配置链

1. 安装目标编译器、CMake、Ninja 和调试器。Arm Cortex-M 通常使用 GNU Arm 工具链与 `arm-none-eabi-gdb`；
2. 在 **Settings | Build, Execution, Deployment | Toolchains** 创建嵌入式工具链，明确指定 C/C++ 编译器、CMake、构建工具和 GDB；
3. 在 **CMake Profiles** 创建 `Debug` 与 `Release` 配置。交叉编译项目应通过 `CMAKE_TOOLCHAIN_FILE` 指向项目内的工具链文件，不把路径散落在源码中；
4. 对 STM32，可先用 CubeMX 生成含 `.ioc`、启动文件、链接脚本和 CMake 配置的工程，再由 CLion 打开。生成器输出发生变化后，重新加载 CMake 并检查链接脚本、源文件列表和宏定义；
5. 创建 OpenOCD 或厂商调试服务器配置，使用与板载调试器匹配的 interface 文件和与具体芯片匹配的 target 文件。不要复制其他型号的 OpenOCD 参数；
6. 在下载后停止于 `main`，确认断点、变量查看和外设寄存器读取正常。若调试器无法连接，优先检查目标电压、SWD 接线、复位与启动模式。

一个最小工具链文件通常明确系统、处理器和交叉编译器，例如：

```cmake
set(CMAKE_SYSTEM_NAME Generic)
set(CMAKE_SYSTEM_PROCESSOR arm)

set(CMAKE_C_COMPILER arm-none-eabi-gcc)
set(CMAKE_CXX_COMPILER arm-none-eabi-g++)
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)
```

工具链文件还需要配合具体芯片的编译选项、链接脚本、启动文件、SDK 和库。示例只说明职责，不能直接用于所有 Cortex-M 型号。

## VS Code + PlatformIO：多板卡与可声明配置

PlatformIO 将板卡、框架、依赖、串口和调试配置放入项目根目录的 `platformio.ini`。每个 `[env:名称]` 对应一个可构建、烧录和调试的目标环境。

```ini
[env:bluepill_f103c8]
platform = ststm32
board = bluepill_f103c8
framework = stm32cube
upload_protocol = stlink
debug_tool = stlink
monitor_speed = 115200
build_type = debug
```

配置后应执行一次构建、上传和调试，确认 `board`、`framework`、上传协议与实际硬件一致。多板卡工程可将公共选项写入 `[env]`，再用多个 `[env:名称]` 区分芯片、优化级别或功能开关；不要把端口号、私有路径和密钥固化在共享配置中。可用 `pio project config --lint` 检查解析后的配置。

## ESP-IDF：以官方工程和组件配置为中心

1. 用 Espressif 提供的安装器或官方脚本安装 ESP-IDF 与对应工具链，进入已导出的 ESP-IDF 终端环境；
2. 从 `get-started/hello_world` 或项目模板开始，执行 `idf.py set-target <目标>` 生成与芯片匹配的构建目录；
3. 用 `idf.py menuconfig` 配置晶振、Flash 模式、分区表、日志级别、Wi-Fi/BLE 等选项，生成的 `sdkconfig` 与默认值文件应纳入版本控制；
4. 使用 `idf.py build flash monitor` 验证编译、串口端口和日志，量产前再单独配置 Flash 加密、安全启动和 eFuse；
5. 在 VS Code 或 CLion 中打开 ESP-IDF 工程时，仍以项目的 `CMakeLists.txt`、组件依赖和 `sdkconfig` 为准，不把 IDE 生成的本地缓存提交进仓库。

## Arduino IDE：从板卡包到串口验证

1. 通过 Boards Manager 安装板卡核心，第三方核心还需要在 Preferences 中加入其官方 Boards Manager URL；
2. 在 Tools 中选择正确的开发板、处理器变体、端口、上传器和 CPU 频率，ESP32 等板卡还要核对 Flash 分区与上传速率；
3. 将第三方核心 URL、库版本、编译选项和最小示例记录在项目 README，避免“本机能编译，其他机器找不到库”；
4. 首次下载后，用串口监视器确认端口和波特率。串口被占用或自动复位异常时，先排查 USB 线、电源和 BOOT/EN 电路。

Arduino IDE 适合快速验证；当工程出现多板卡、严格依赖版本、单元测试或持续集成需求时，可迁移到 PlatformIO 或原生 SDK。

## Keil MDK：Pack、工程选项与下载器

1. 通过 Pack Installer 安装目标芯片的 Device Family Pack，建立工程时选择准确的 Device；
2. 在 **Options for Target** 中核对晶振频率、C/C++ 宏、优化级别、包含路径和生成 ELF/HEX 的选项；
3. 将启动文件、链接/Scatter 文件和用户配置文件纳入版本控制，避免只提交 `.uvprojx` 而遗漏构建边界；
4. 在 Debug 页选择 ST-LINK、J-LINK 或 CMSIS-DAP，核对 Reset、Flash Download Algorithm 与目标 Flash 容量；
5. 先以 Debug 配置验证断点、寄存器与下载，再切到 Release 配置检查代码尺寸、栈和映射文件。

## Pico SDK：CMake、PICO_SDK_PATH 与 picotool

1. 获取 Pico SDK 与示例，安装 ARM GCC、CMake 和 Ninja；
2. 以环境变量或 CMake 缓存设置 `PICO_SDK_PATH`，再由顶层 `CMakeLists.txt` 导入 SDK；
3. 在工程中设置目标板、USB/UART 标准 I/O 和目标名称，生成 UF2、ELF 和映射文件；
4. 首次上板时按住 BOOTSEL 进入 USB 大容量存储模式，复制 UF2；随后可使用 Picoprobe、SWD 或 `picotool` 建立调试与烧录流程；
5. 将 `CMakeLists.txt`、SDK 提交方式、工具链版本和板型定义纳入版本控制，不提交构建目录。

## 配置文件应怎样进入版本控制

| 环境 | 应提交 | 不应提交或应忽略 |
|---|---|---|
| STM32CubeIDE | `.ioc`、启动文件、链接脚本、项目设置、源代码 | 构建输出、用户工作区缓存 |
| CLion | `CMakeLists.txt`、工具链文件、OpenOCD 配置、共享运行配置 | `cmake-build-*`、个人路径和本地缓存 |
| PlatformIO | `platformio.ini`、`src/`、`lib/`、`test/` | `.pio/`、本机端口配置 |
| ESP-IDF | `CMakeLists.txt`、组件文件、`sdkconfig`、默认配置、分区表 | `build/`、下载缓存 |
| Arduino IDE | `.ino`、依赖清单、第三方核心 URL 与版本记录 | 个人偏好和临时编译目录 |
| Keil MDK | 工程文件、Pack 版本记录、启动/Scatter 文件 | `Objects/`、`Listings/`、用户布局文件 |
| Pico SDK | `CMakeLists.txt`、SDK 版本记录、板型配置 | `build/`、生成的 UF2/ELF，除非作为发布产物 |
